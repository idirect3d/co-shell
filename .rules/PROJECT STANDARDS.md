
co-shell 项目开发规范

> 本文件是人与 AI 协作开发的统一约定，每次开发会话都应遵守。
> 设计决策与需求演进见 `ROADMAP.md`（单一事实源）；架构与功能全景见 `docs/DESIGN.md`（阶段性设计文档）；本文件只定"怎么干活"。

## 项目简介

co-shell：AI 驱动的智能命令行 Shell（REPL），支持多模型、多模式、工具调用、Web 服务端渲染 UI、飞书/移动端桥接、任务计划、记忆、调度等能力。
Go 1.25 + bbolt（本地存储，可选 PostgreSQL）+ 服务端渲染 Web UI，Agent 执行复用 kimi-cli / cline 等成熟 CLI 引擎。

## .rules/ 按需加载机制（FEATURE-417）

`.rules/` 根目录下的 `.md` 文件会**始终加载**到系统提示词 RULES 节（核心规范）。

`.rules/` 下的**子文件夹**采用**按需加载**：子文件夹名 + 完整路径会加载到系统提示词（作为"可用规则类型"提示），但子文件夹内的文件内容**不会**加载。需要时用 `read_file` 读取对应路径。

当前按需加载的规则类型：
- `前端控件使用规范` → `.rules/前端控件使用规范/`（开发 Web UI 前端控件时读取，内含通用约定/基础按钮控件/容器及布局控件等分文件）

## 分支策略（trunk-based）

> **🚨 最高优先级红线（不可违反）**：**禁止直接在 `main` 分支上提交任何代码修改**。任何代码修改（包括标题栏优化、颜色优化、冒号优化等小改动）都必须在功能分支上开发、提交、合并。违反此红线视为严重违规，必须立即纠正（将 main 上的提交迁移到功能分支）。

> **核心原则：一个会话一个分支**。每个会话通常已经在一个功能分支上，因此**不是每个用户修改指令都需要创建分支**——仅当当前会话中**尚未创建分支**时才自动创建分支。会话内后续的所有修改指令都在当前分支上继续，不再重复建分支。

- `main` 始终处于可发布状态，**禁止直接在 main 上提交**（最高优先级红线，见上）
- 功能分支命名：`FEATURE-XXX`（新能力）/ `FIX-XXX`（修复），**两类共用同一编号序列**，编号接续 ROADMAP 任务记录中的最大编号
- **一个会话一个分支**：会话开始时若尚未在功能分支上，则自动创建分支；会话内后续指令沿用该分支，不重复建分支
- 分支短命（目标 <3 天），完成后 squash merge 回 `main` 并删除分支
- 开工前确认当前在 `main` 且无未合并分支阻塞

## 新建开发任务

> **核心原则：一个会话一个分支**。每个会话通常已经在一个功能分支上，因此**不是每个用户修改指令都需要创建分支**——仅当当前会话中**尚未创建分支**时才自动创建分支。会话内后续的所有修改指令都归入该会话已确定的任务编号与分支下，不再重复建分支。

0. **前置检查**：当用户开始一个新任务时，先执行 `git branch --show-current` 确认当前分支状态。
   - 若当前已在功能分支（`FEATURE-XXX` / `FIX-XXX`）：直接沿用该分支，进入步骤 2 确认任务编号与版本号。
   - 若当前在 `main` 分支：进入步骤 1 创建分支。

1. **确认版本归属（新建任何分支前必做）**：新建任何分支前（包括 feature 和 fix），都需要让用户确认新建分支的成果将放到哪个版本。用户明确之后，先更新 ROADMAP 中的版本计划下对应的内容（若该版本计划不存在则新建一组该版本的版本计划作为**当前版本**，后续分支都加到该版本下）。若用户选择新建版本，则根据用户的选择更新 main.go 中的 version 尾数（+1）。

   **版本号默认递增规则**：当用户未明确指定版本时，按分支类型默认递增——**FEATURE 分支（新功能）→ 版本号第二位（minor）递增**，**FIX 分支（Bug 修复）→ 版本号第三位（patch）递增**。该规则为默认值，用户可手动覆盖；**major（第一位）递增仍由用户手动决定**（重大变更需人工判断）。

2. **确认任务编号**：根据任务指令更新 ROADMAP 中的任务信息（需要新增或修改某一个特性或修复任务），获得本次任务编号（格式：`FEATURE-XXX` / `FIX-XXX`），编号应为 ROADMAP 中未被FEATURE和FIX使用的最小编号（与BUILD编号无关），任务记录需要追加到当前版本的最后一个任务。**注意：用户确认测试验证通过之前不要标记完成**。

   **任务编号在会话开始时确定一次**：会话内后续的所有修改指令都归入该任务编号下，不再为每个指令新建任务编号。若当前会话已存在任务编号（已在功能分支上），直接沿用，无需重复建号。

3. **新建分支（仅当当前会话尚未创建分支时）**：若当前在 `main` 分支，则基于任务编号创建新分支（如：`git checkout -b FEATURE-XXX`），禁止直接在main分支上提交任何修改。若当前已在功能分支，跳过此步，直接在当前分支上继续开发。

4. **构建测试用例（需求规格阶段同步生成）**：在确定开发需求规格阶段，应**同时**生成测试用例到固定位置 `use-case/{分支名}/`，命名 `{分支名}-UC-XXXX.md`（如：use-case/FEATURE-051/FEATURE-051-UC-0015.md）。应使用循环模式确保测试用例中有足够数量的运行时用例，以便能够通过对案例结果的确认就能达成应有的质量目标。用例生成后需要提示用户确认，确认后方能开始执行实施流程。

5. **开发编码**：用户确认可以开始开发后开始执行实施流程：dev.md。

**注意**：git操作不要用那种需要用户响应的命令，以免因此中断开发过程！

## 开发流程
**总则**：只要存在代码修改，在报告用户完成之前，必须先编译生成可执行码（`go build -o work/co-shell .`），确保交付的是可运行的最新版本。**每次编译前，都需要更新 main.go 中的 build 计数（+1）**，以便区分编译后可执行码的不同版本。

> **会话内循环**：一个会话内可能包含多次编码-编译-提交循环，每次循环都更新 BUILD 编号并提交到**当前分支**（不合并）。只有用户完整确认后，才执行合并（见「代码提交及合并」章节）。

0. **强制分支检查（编码前必做）**：开始编码前，先执行 `git branch --show-current` 确认当前在功能分支（`FEATURE-XXX` / `FIX-XXX`）。**若当前在 `main` 分支，必须先建任务编号并创建功能分支，禁止在 main 上直接编码**。若当前已在功能分支，直接沿用，不重复建分支。

1. **开始编码**：根据任务描述和测试用例进行开发编码（如果以上两项上不明确，应提示用户提供缺失的信息再继续）。**编码以测试用例为指引，明确每个环节的目标**。注意：在修改任何程序文件前，必须先说明：本次修改是解决什么问题、修改这个文件的原因是什么、准备怎么修改。

2. **单元测试**：根据当前任务构建的测试用例，对程序进行循环测试验证，对发现的问题进行整改。**开发验证以测试用例结果为主要抓手，原则上所有测试用例通过才能进入下一个环节**，直到所有测试用例通过并达成任务目标。

3. **更新构建信息**：更新 main.go 中的 build计数（+1），以便能够区分编译后可执行码的不同版本。根据任务实际情况，更新ROADMAP.md中的对应任务描述和执行状态，在任务描述结尾标注build计数 `[BUILD-YYYY]`（有效数字前不用补零）。**每次编码完成、编译、提交、测试后都要更新 BUILD 编号**。

4. **编译代码**：一次性完整运行 `go build ./... && go vet ./... && go build -o work/co-shell .`，同时执行（**禁止分开执行**）验证编译、检查代码质量并编译可执行程序到测试文件夹下。

5. **提交代码**：提交代码到**当前分支**（不合并到 main）。

6. **等待用户确认**：使用 `attempt_completion` 工具明确询问用户 "测试是否通过，是否可以继续'合并代码'（工作流: /merge）"。**只有用户完整确认后，才执行合并**。

**注意**：不要通过写长shell命令，或者直接在命令行写python代码的方式做事！

## 编译可执行码
1. 没有参数：仅编译当前操作系统的版本到work/下，命名为co-shell，**需递增 build no**。
2. 参数为3时：编译MacOS Arm、Windows x86、Linux Arm几个版本到work/下，生成文件命名规范 `co-shell-{version}-{os}-{arch}[.exe]`，**不用递增 build no**。
3. 参数为release时：编译MacOS、Windows、Linux三个操作系统的Arm版和X86版到dist/Release/下，生成文件命名规范 `co-shell-{version}-{os}-{arch}[.exe]`，**不用递增 build no**。

## 代码提交及合并

> **合并时机**：会话内多次编码-编译-提交都留在当前分支，**只有用户完整确认后**，才自动执行打版本标签、编译、提交、合并代码。

1. **更新构建信息**：如有未提交的更新，则更新 main.go 中的 build计数（+1），以便能够区分编译后可执行码的不同版本。根据任务实际情况，更新ROADMAP.md中的对应任务描述和执行状态，在任务描述结尾标注build计数 `[BUILD-YYYY]`（有效数字前不用补零）。

2. **编译代码**：一次性完整运行 `go build ./... && go vet ./... && go build -o work/co-shell .`，同时执行（**禁止分开执行**）验证编译、检查代码质量并编译可执行程序到测试文件夹下。

3. **强制分支确认（提交前必做）**：提交前先执行 `git branch --show-current` 确认当前在功能分支。**若当前在 `main` 分支，禁止提交，必须先建任务编号并创建功能分支**。确认在功能分支后，提交最后更改的代码到当前分支，合并当前分支到main分支。

4. **打版本标签（仅合并到 main 时）**：合并到 main 分支时，按版本计划打版本标签（以当前版本号打一个版本标签）。**仅提交到其他分支时不打版本标签**。

**注意**：以上步骤在**用户完整确认后**自动执行——用户确认测试通过后，自动编译、提交、合并代码；合并到 main 时按计划打版本标签，仅提交到其他分支时不打版本标签。

## 依赖策略

- **标准库优先**；仅当标准库无对应能力时，引入该领域事实标准的单一依赖
- 当前允许的例外：`github.com/gorilla/websocket`（WebSocket）、`github.com/jackc/pgx/v5` / `github.com/lib/pq`（PG 驱动）、`go.etcd.io/bbolt`（本地 KV 存储）、`github.com/mark3labs/mcp-go`（MCP）、`github.com/larksuite/oapi-sdk-go/v3`（飞书）、`golang.org/x/crypto`（bcrypt 口令哈希）
- 新增任何依赖前需在 ROADMAP 决策记录中登记理由

## Web UI 前端信息刷新原则

Web UI 前端展示的所有信息（文件状态、任务进展、状态栏等）必须保持与后端最新状态一致。刷新时机遵循以下原则：

- **状态栏（token 统计等）**：在接收每个 LLM 内容块（token_iter 等）时刷新——实时、前端本地计算、无后端调用、开销小。
- **文件状态、任务进展**：在**工具调用完成时**（TOOL result）刷新——只有工具调用才可能改变文件/任务状态，避免每个 LLM 块都触发后端 API 调用造成性能开销。
- **切换会话（session）时**：必须主动推送一次任务进展刷新给前端——切换会话会改变后端任务计划，前端需同步刷新，否则显示旧会话的任务进展。

**总则**：任何导致后端状态变化（文件、任务、会话、token 统计）的操作，都必须确保前端在合理时机刷新对应信息，不得出现前端显示与后端实际状态不一致的情况。

## 常用命令

```bash
go test ./... -short                                      # 跳过集成/真实依赖测试
go test ./<pkg>/ -v                                       # 单包测试
go run . run --workdir <wt> --prompt "..." [--session <id>]   # 运行 Agent
go run . --serve --port <port>                            # 启动 Web UI（--dev 从磁盘热加载）
./build-release.sh <版本号>                                # 全平台 Release 构建（dist/<版本号>/）
```

> **Web UI 测试规范**：需要测试 Web UI 时，**必须使用 `--serve` 参数**启动（不自动打开浏览器）。若不带 `--serve` 直接运行，默认模式会自动打开系统浏览器，该浏览器会占用 WebSocket 单客户端连接，影响你使用调试浏览器（browser_* 工具）进行调试。

> **进程管理安全**：注意 —— 除非你确认你 kill 的不是你自己，否则不要轻易 kill co-shell 进程。co-shell 进程可能承载当前会话或用户正在使用的实例，误杀会导致会话中断或数据丢失。
