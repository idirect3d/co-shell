# FIX-320: execute_command 超时 goroutine 误杀后台任务修复

## 背景

`executeSystemCommand()`（LLM 路径）使用独立的超时 goroutine 管理命令超时：

```go
if effectiveTimeout > 0 {
    go func() {
        time.Sleep(effectiveTimeout * time.Second)
        timedOut.Store(true)
        killProcessGroup(cmd)   // 到点无条件 kill(-pid)
    }()
}
err := cmd.Wait()
```

两个缺陷：

1. **命令提前结束时超时 goroutine 残留**：命令在超时前正常退出（`cmd.Wait()` 返回），但 goroutine 仍持有已退出 bash 的 PID 在 `Sleep`，到点照样 `kill(-pid)`。若后台子进程（如 `sleep 300 &`）仍留在原进程组，会被误杀。
2. **REPL 路径未设置进程组**：`ExecuteCommandDirectly()` 用 `exec.CommandContext`，两条分支都没调 `setProcessGroupAttr(cmd)`，与 LLM 路径不一致。`python3 | head` 这类管道命令超时时只杀 bash，孙进程泄漏。

## 修复方案

### `agent/command_tools.go` — LLM 路径 `executeSystemCommand()`

- 引入 `done` channel，在 `cmd.Wait()` 返回后 `close(done)` 通知超时 goroutine。
- 超时 goroutine 改为 select 监听：`done` 已关闭（命令已结束）→ 放弃 kill；`time.After` 到点 → 执行 `killProcessGroup`。
- `cmd.Wait()` 返回后调用 `cmd.Process.Release()`，释放 PID 资源，避免 PID 复用风险。

### `agent/command_tools.go` — REPL 路径 `ExecuteCommandDirectly()`

- 两条分支（有超时/无超时）均补调 `setProcessGroupAttr(cmd)`，与 LLM 路径一致，使管道孙进程超时后也能被进程组 kill 连锅端。

### 测试

本用例通过运行时验证，不新增单元测试文件。

## 用例列表

### UC-0001 命令提前完成，超时 goroutine 不误杀后台任务（修复前必现误杀）

**前置条件**：
- 配置 `cmd-timeout=3`（`co-shell --cmd-timeout 3`）。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 3`。
2. 输入指令（LLM 路径）：让 LLM 执行 `sleep 300 & echo done`（后台启动 300 秒睡眠任务，bash 立即返回）。
3. 观察工具立即返回 `done`（不等待 3 秒超时）。
4. 等待 4 秒以上（超过配置的 3 秒超时窗口）。
5. 在另一个终端执行 `ps aux | grep "sleep 300"`。

**预期**：
- 步骤 3：工具调用立即返回，输出含 `done`，无超时错误。
- 步骤 5：**`sleep 300` 后台进程仍然存活**（不会被误杀）。
- 修复前：步骤 5 中 `sleep 300` 进程已被 SIGKILL（误杀）。

### UC-0002 命令未完成，超时仍正常触发进程组 kill

**前置条件**：
- 配置 `cmd-timeout=2`。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 2`。
2. 输入指令（LLM 路径）：让 LLM 执行 `sleep 60`（长时间阻塞命令）。
3. 等待 2 秒超时触发。

**预期**：
- 工具调用返回超时错误：`command timed out after 2 seconds`。
- `ps aux | grep "sleep 60"` 查无进程（进程组被 kill）。

### UC-0003 REPL 直接命令管道孙进程超时后被杀（进程组设置生效）

**前置条件**：
- 配置 `cmd-timeout=2`。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 2`。
2. 在 REPL 直接输入命令（非 LLM 路径）：`sleep 60 | cat`。
3. 等待 2 秒超时触发。

**预期**：
- 命令返回超时错误。
- `ps aux | grep "sleep 60"` 查无进程（管道两个子进程均被进程组 kill，修复前 `sleep 60` 孙进程泄漏存活）。

### UC-0004 无超时配置（cmd-timeout=0）后台任务不受中断

**前置条件**：
- 配置 `cmd-timeout=0`（默认，无限制）。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 0`。
2. 输入指令（LLM 路径）：让 LLM 执行 `sleep 300 & echo done`。
3. 观察工具立即返回 `done`。
4. 等待 2 秒。
5. 另一终端执行 `ps aux | grep "sleep 300"`。

**预期**：
- 步骤 3：工具立即返回。
- 步骤 5：`sleep 300` 进程存活（cmd-timeout=0 不启动超时 goroutine，无中断机制）。

### UC-0005 超时 goroutine 在命令结束后不泄漏（PID 资源释放）

**前置条件**：
- 配置 `cmd-timeout=5`。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 5`。
2. 输入指令（LLM 路径）：让 LLM 连续执行 5 次 `echo hello`（每次立即返回）。
3. 每次工具调用立即返回。
4. 整个过程不超过 5 秒（第 5 次执行完成后立即观察）。

**预期**：
- 每次工具调用立即返回，无超时误报。
- `ps aux | grep "sleep 60"` 无残留进程。
- 命令完成后 `cmd.Process.Release()` 已调用，PID 资源释放（无句柄泄漏，进程数不持续增长）。

### UC-0006 超时 goroutine 到点不误杀已退出的进程组（PID 复用保护）

**前置条件**：
- 配置 `cmd-timeout=3`。
- 操作系统为 Unix（macOS/Linux）。

**步骤**：
1. 启动 co-shell：`co-shell --cmd-timeout 3`。
2. 输入指令（LLM 路径）：让 LLM 执行 `sleep 1 & echo done`（bash 立即返回，后台 sleep 1 秒自动结束）。
3. 观察工具立即返回 `done`。
4. 等待 4 秒以上（超过 3 秒超时窗口）。
5. 另一终端执行 `ps aux | grep "sleep 1"`。

**预期**：
- 步骤 3：工具立即返回。
- 步骤 5：无 `sleep 1` 残留（后台任务自然结束，未被误杀——与 UC-0001 配合验证 done channel 关闭后 goroutine 放弃 kill）。
