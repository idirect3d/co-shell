# FIX-555 验收测试用例：token 用时/速度计时修复（stamp 生命周期 / 口径统一 / 缺失路径 / 展示时机）

> 需求（用户提出）：「每轮迭代的 token 使用情况中的速度计算似乎有误差，感觉是计时不对，有的时候明显有较长用时的情况，
> 显示的用时偏短或接近0。仔细调查现在的 token 用时，从什么时候开始，到什么时候结束，有没有漏掉一些 LLM 输出的环节？
> 或者加入了一些不必要的工具调用用时。**工具调用的输出也要算进来，但执行不要放**。」
>
> 调查结论（修复前的计时链路）：
> - 起点 `llmCallStartTime`：`stream_response.go` 中于 `ChatStream()` 之前设置（不含 `buildContextMessages()`）；
> - 首 token `firstTokenTime`：第一个 content / reasoning / **tool_call delta** 事件被消费时；
> - 终点 `llmStreamEndTime`：收到 `StreamEventDone` 时；
> - 工具**执行**在流结束之后，不计入（符合需求）；工具调用**参数生成**已计入（`isFirstTokenEvent` 含 ToolCallDelta，FIX-545）；
> - 缺陷：`GetLLMTiming()` 的 token 分子取「上次消费以来的累计差值」而分母只覆盖最后一次调用 → 速率虚高、用时只反映最后一次；
>   stamp 仅在 `GetLLMTiming` 消费时清零、`totalDelta==0` 早退不清理 → 实测出现 `ttft=-35.648s / out=7200.992s`（2026-09-23 15:27:00）；
>   非流式回退（`nonStreamingFallback`）与 `run.go` 的 `Run` 不写 stamp → token 照记但用时显示 "-"；
>   `token_iter` 在迭代末尾（工具执行完之后）才发出 → 用户先看到长等待、后看到与该等待无关的用时。
>
> 设计口径（经 ask_user 与用户确认）：
> - 版本归属 **v0.74.1**，任务编号 **FIX-555**，分支 **FIX-555**；
> - 修复范围 = **① stamp 生命周期 + ② 口径统一 + ④ 补齐缺失路径 + ⑤ 展示时机**；
> - **不做** ③ 异常值兜底（不隐藏、不标记、不回退异常值，保留原值与现有展示形式）。
> - 实现约束（保持口径一致）：
>   - 每次 LLM 调用由调用方显式开始一个测量窗口（`beginLLMCall(false)`），重试时以 `beginLLMCall(true)` 延续上一次的开始时刻，
>     使**一次迭代 = 一行统计**，且该行的 token 与用时来自同一次调用；
>   - 非流式（无增量事件）路径只能测得整段墙钟，按 `token_usage` 表既有约定写入两个窗口（用时视为近似值，Web UI 已有近似提示）；
>   - `IterTokenDelta()` / `<context_window>` / 上下文溢出判断仍取「最近一次调用」，本次不改变其语义。

> **权威计时口径（用户原述，2026-09-25）**：
> 「我希望每次迭代，即提交一次请求给 LLM，从提交开始，到返回第一个字符开始，这段时间算做**输入处理时长**，
> 作为输入处理速度的分母。从返回第一个字符开始，一直到 LLM 返回本轮所有内容（含 LLM 思考、正文、以及所有工具调用内容）
> 结束所用时长是**输出时长**，作为输出处理速度的分母。」
>
> 即：① 一次 LLM 请求 = 一次测量；② `ft` = 提交 → 首个输出字符；③ `out_dur` = 首个输出字符 → 本轮全部内容结束
> （思考 + 正文 + 全部工具调用参数；工具**执行**不在其中）；④ 速率的分母即上述两项时长，分子为同一次请求的 usage。

- 基线记录：修复前后各跑一轮相同任务，对比 token 行的 `↑（速率, 用时）↓（速率, 用时）`。

### UC-001 单轮流式调用：token 行发出于工具执行之前

- 前置：修复后的可执行码，`token-usage=on`；`show-tool-output=on` 便于观察顺序。
- 步骤：发一条会触发 1 个工具的任务（如「列出当前目录」）。
- 期望：消息流内顺序为 `LLM 输出块 → token 统计行 → TOOL 块（含执行结果）`；token 统计行**不再**出现在 TOOL 块之后。

### UC-002 正常一轮的用时与速率自洽

- 步骤：执行一轮较长输出的任务（如「写 200 字说明」），记录 token 行的 `↑p（in_tps, ft） ↓c（out_tps, out_dur）`。
- 期望：`out_tps × out_dur ≈ c`（相对误差 ≤ 10%）；`out_dur` 与肉眼观察的流式输出时长接近（不出现「等了很久却显示 0.0s」）；
  `ft` 与「按下回车到首个字出现」的间隔接近。

### UC-003 引擎未回报 usage 的轮次不污染下一轮

- 前置：临时把引擎切到不回报 usage 的配置（或用桩服务只回 `[DONE]`）。
- 步骤：先跑一轮不回报 usage 的任务，再跑一轮正常任务。
- 期望：**无 usage 的那一轮** timing 三项均为 `-`（不显示 0 或乱值）；**下一轮**的 `ft` 为正数且 `out_dur` 合理，
  不出现负数、也不出现跨越上一轮的巨大值。

### UC-004 上一轮 stamp 不再泄漏

- 步骤：连续跑两轮（第二轮耗时明显长于第一轮），记录两轮的 `ft`。
- 期望：两轮 `ft` 均为正；`ft + out_dur ≤ 该轮实际墙钟耗时`；第二轮 `ft` 不出现负值或跨轮累计值。

### UC-005 落库记录不含负值/超长值

- 步骤：跑完上述用例后，用只读快照读取 `token_usage`（新写入的记录）。
- 期望：新增记录的 `first_token_sec ≥ 0`、`output_sec ≥ 0`；不存在 `first_token_sec < 0` 或 `output_sec` 远超实际墙钟的记录。

### UC-006 走 continue 的迭代不再让速率虚高

- 前置：`no-tool-action=prompt`（该策略下 0 工具调用会 continue 再问一次）；引擎回报 usage。
- 步骤：发一条会让模型先做一段纯文字回答、再进入下一轮的任务。
- 期望：**每一次 LLM 调用各出一行** token 统计（不把两次调用合并成一行）；每行速率与其自身 token 数一致；
  不出现「token 数是单次的、用时也是单次的、但速率明显偏大」的情况。

### UC-007 速率与所显示 token 数同源

- 步骤：任取一轮，用该行 `out_tps / out_dur / c` 三个值互算。
- 期望：`c / out_dur ≈ out_tps`（相对误差 ≤ 10%），即三者来自同一次调用。

### UC-008 仅 tool_calls 无 content 的轮次仍有用时与速率（FIX-545 回归）

- 前置：OpenAI 工具调用模式（`send-tools`），工具参数较长（如 `write_to_file` 写 100 行）。
- 期望：该轮 token 行的 `out_dur` 与 `out_tps` 均有值（非 `-`），且 `out_dur` 与工具参数流式输出的时长相符。

### UC-009 连续多轮：速率无异常值

- 步骤：连续完成一个 5 轮以上的任务。
- 期望：每轮 `out_tps` 落在合理区间（本机实测约 200–400 t/s），不出现 `>1000 t/s` 的异常值。

### UC-010 非流式回退路径不再全显示 "-"

- 前置：使 `ChatStream` 不可用（如指向不支持 SSE 的兼容端点），触发 `nonStreamingFallback`。
- 期望：该轮 token 行的 `ft`（输入处理时长）与**输入速率**有值，取整段请求墙钟（无增量事件时首个字符不可观测）；
  **`out_dur` 与输出速率显示 `-`** —— 无法观测的生成窗口不虚报；
  落库沿用 FEATURE-546 既有约定（`first_token_sec = output_sec = 墙钟`），供趋势图使用（用量面板已有「非流式速率为墙钟近似」提示）。

### UC-011 ESC 中断后继续：合并为一行

- 步骤：任务进行中按 ESC → 选择「继续」。
- 期望：该迭代**只出一行** token 统计；`ft`（或 `ft+out_dur`）覆盖两次尝试的**总等待**，而不是只反映重试的那一次；
  重试的第二次调用不额外产生第二行。

### UC-012 `:debug on` 切换后重试：同样只出一行

- 步骤：任务进行中按 ESC → 输入 `:debug on`（触发重试分支）。
- 期望：与 UC-011 相同；且 `:debug on` 生效的提示正常显示。

### UC-013 重试后工具执行与历史消息完整

- 步骤：ESC → 继续，让该轮继续执行工具直至完成。
- 期望：工具正常执行；`/api/session` 或 `:context` 中该轮**只有一条** assistant 消息（无重复、无缺失）；
  工具结果消息完整。

### UC-014 token 行在消息流中的位置

- 步骤：对照 UC-001 的流式界面。
- 期望：token 统计行紧跟本轮 LLM 输出块之后；同一轮的 TOOL 块位于其下方；刷新历史（回放）后位置一致、不重复出现。

### UC-015 长工具执行时 token 行在工具开始前已可见

- 步骤：让模型调用一个耗时 10 秒以上的工具（如 `execute_command` 执行 `sleep 12`）。
- 期望：token 统计行在工具**开始执行时**就已显示（不是等 12 秒工具跑完后才出现）；
  该行的 `out_dur` 只反映 LLM 生成时长，**不含**这 12 秒工具执行时间。

### UC-016 ctx_index 语义

- 步骤：完成一轮后，把 token 行前缀的序号与该轮 LLM 实际看到的上下文（`:context` 或 `/api/session` 中的消息序列）对照。
- 期望：序号等于该轮 LLM 调用**实际发出的上下文中最后一条消息**的序号（即 assistant 回复之前的最后一条）；
  该序号在同一轮的所有 token 行中一致。

### UC-017 会话累计包含此前漏计的调用

- 步骤：跑一个含 `no-tool-action=prompt` 继续轮的任务，记录状态栏 Session ↑↓ 与消息流中各 token 行的累加值。
- 期望：Session 累计 ≈ 所有 token 行 `↑/↓` 之和（此前走 continue 的调用完全不进累计，现在应计入）。

### UC-018 `/api/usage` 速率趋势图正常

- 步骤：打开用量面板（含「每日平均速度」图）。
- 期望：图表正常渲染，无 `NaN`、`Inf` 或缺值崩溃；历史日期（2026-09-20 之前无计时）仍按原规则跳过，不因本次修改而变化。

### UC-019 `<context_window>` 百分比仍取最近一次调用

- 步骤：让任务连续跑 2 轮以上，观察下一轮消息附带的 `<context_window>` 数值。
- 期望：仍等于**最近一次** LLM 调用的 total tokens 与模型上限之比（本次未改变该语义，不得变成累计值或 0）。

### UC-020 上下文溢出保护阈值判断仍取最近一次调用

- 前置：`context-policy=reorganize`，阈值设为较低值（如 30%）。
- 期望：阈值判断行为与修复前一致（仍基于最近一次调用的 total tokens），不因计时改动而提前/延后触发。

### UC-021 视觉识别轮的 token 行

- 前置：`vision-context-mode=minimal`，提供一张图片并触发 `visual_analysis`。
- 期望：识别轮调用完成后**立即**发出该轮 token 行（在识别结果回填之前），数值为视觉模型的用量；
  不出现「识别轮的 token 行缺失」或「与主模型轮合并成一行」。

### UC-022 缓存命中率显示不受影响

- 期望：token 行的 `cache_rate`（KV 缓存命中率）仍正常显示；引擎未回报 `prompt_tokens_details` 时该字段缺席（不显示 0%）。

### UC-023 `token-usage=off` 时不发 token 行

- 步骤：`.set token-usage off` 后跑一轮任务。
- 期望：消息流内不出现 token 统计行，也不影响任务执行与其它事件。

### UC-024 单元：GetLLMTiming 单次调用口径

- 步骤：`go test ./agent/ -run TestFIX555 -v`
- 期望：① 只使用本次调用的 prompt/completion 与本次时间戳，速率 = 本次 tokens / 本次窗口；
  ② 本次未回报 usage → 返回空值，**且时间戳被清理**（再次读取不会重复上报上一轮窗口）。

### UC-025 单元：beginLLMCall 清零与 resume 语义

- 期望：`beginLLMCall(false)` 后三个时间戳中 `firstToken`/`end` 为空、`start` 为当前时刻；
  连续两次 `beginLLMCall(false)` 之间不残留上一轮的 `firstToken`/`end`；
  `beginLLMCall(true)`（重试）保留上一次的 `start` 但清空 `firstToken`/`end`，使窗口覆盖两次尝试的总等待。

### UC-026 单元：非流式路径补 stamp

- 期望：模拟非流式调用（有 usage）后，`GetLLMTiming()` 的 `FirstTokenLatency` 与 `InputTPS` 有值（整段墙钟），
  而 `OutputDuration` / `OutputTPS` 为 `-`；时间戳满足 `start ≤ firstToken = end`。

### UC-027 单元：emitIterTokenStats 门控

- 期望：`token-usage=off` 时不发出事件；`total tokens = 0` 时不发出事件；正常情况发出且带 `out_dur`/`cache_rate` 等 meta。

### UC-028 编译、静态检查与全量测试通过

- 期望：全部通过，无新增告警。
