# FEATURE-566 运行时用例 UC-0007：多个子代理先后完成 → 逐条通知（先到者起迭代，其余落动态感知）

## 目标

验证多个子代理（A1、A2，乃至 A1..A5）先后结束时，通知**逐条**产生且**每条都被处理**：先完成者在主 agent 空闲时起一次新迭代；其后完成的（此时主 agent 已忙碌）通过动态感知注入该迭代，不丢、不重、不丢次序。

## 前置条件

- `work/` 下已构建本分支可执行码（v0.80.0）；以 `--serve --port <port>` 启动，Web UI 已连接。
- `max_sub_agents >= 3`。

## 步骤

1. 输入：「用 launch_sub_agent 同时启动 A1（`sleep 8`）、A2（`sleep 14`）、A3（`sleep 20`），timeout_seconds 设 3」。回合结束后保持空闲。
2. 观察 t≈8s：A1 结束。
   - 预期：主 agent 空闲 → 起一次新迭代，通知（A1）作为正式 user message 出现；该迭代开始运行（`IsBusy()=true`）。
3. 观察 t≈14s：A2 结束（此时上一步的迭代可能仍在跑）。
   - 预期：**不再起第二次并行迭代**，A2 的完成事件走动态感知注入当前迭代。
4. 观察 t≈20s：A3 结束，同上注入。
5. 在步骤 3/4 的迭代结束时检查 LLM 输入。
   - 预期：`<user_dynamic_events>` 中存在 A2、A3 的完成条目，各一条，顺序为 A2、A3。
6. 最终用 `sub_agent_status` 复核三者状态与 run。

## 预期结果

- 通知不丢失：A1/A2/A3 三条都能被主 agent 感知。
- 不出现"每次完成都起新迭代"导致的并发迭代；也不出现"多个通知被合并成一条而丢信息"。
- 顺序与完成先后一致。

## 验证方式

- 后端日志中"起新迭代"仅出现一次（A1）；A2/A3 记录为动态事件注入。
- 单元测试补充：连续两次完成回调，第一次走"起新迭代"、第二次（IsBusy=true）走 AddDynamicEvent；事件队列两条。
