# FEATURE-566 运行时用例 UC-0002：子代理失败（非零退出）同样必须通知主 agent

## 目标

验证子代理**失败结束**（exit code != 0，Status=Failed）与正常完成一样会通知主 agent，且通知中能看出是"失败"而不是"完成"，避免主 agent 以为任务成功。

## 前置条件

- 工作区为 co-shell 仓库，`work/` 下已构建本分支可执行码（v0.80.0）。
- 以 `--serve --port <port>` 启动，Web UI 已连接。

## 步骤

1. 输入：「用 launch_sub_agent 启动 A1，指令为 `exit 3`，timeout_seconds 设 60」。
   - 预期：`launch_sub_agent` 在等待窗口内返回该子代理已结束，exit code = 3、状态失败。
2. 观察本回合结束后是否会再出现一次"完成/失败通知"。
   - 预期：**不应重复通知**已经在本回合内被同步返回结果（`WaitTimedOut=false`）的子代理；避免同一事件二次打扰。
3. 输入：「用 launch_sub_agent 启动 A2，指令为 `sleep 15 && exit 7`，timeout_seconds 设 3」，随后本次回合自然结束并保持空闲。
   - 预期：约 15 秒后出现通知，正文明确标注 A2 **失败**（含 exit code）。
4. 重复失败场景但用不同失败方式（如指令引用不存在的命令），确认仍然通知。

## 预期结果

- 成功与失败**都**产生通知（用户要求"不论成功或者失败"）。
- 通知语义正确：失败不得被表述为"完成/成功"。
- 已被同步等待并拿到终态的子代理不再重复通知（若实现选择"一律通知"，需在用例结论中记录该差异并由用户确认）。

## 验证方式

- Web UI 通知正文与 `sub_agent_status` 查到的状态一致（Failed + 相同 exit code）。
- 单元测试补充：`reap` 中 `Status=Failed` 也必须触发完成回调；同步等待（未超时）路径的通知策略有明确断言。
