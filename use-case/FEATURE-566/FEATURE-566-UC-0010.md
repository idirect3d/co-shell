# FEATURE-566 运行时用例 UC-0010：主 agent 已退出 / 无 IO 时通知不崩、不误报

## 目标

验证边界场景：当主 agent 进程已退出（或没有可用的 UserIO / 无 Web 会话）时，子代理结束**不得导致 panic、死锁或状态误报**；落库的终态必须正确（不残留 running）。

## 前置条件

- `work/` 下已构建本分支可执行码（v0.80.0）。
- 具备"父进程先退出、子进程仍在运行"的操作条件（例如单命令模式启动一个长 `sleep` 子代理后结束父进程；或单测中以桩模拟无 IO 的 Agent）。

## 步骤

1. 启动一个 `sleep 60` 子代理（timeout 3），待其转入后台后**退出父进程**（正常退出路径；不要 kill 用户的 serve 实例 pid 2391）。
2. 等待 ~60 秒让子代理自行结束。
   - 预期：无崩溃日志、无 goroutine 死锁告警；子代理进程自行结束。
3. 重新启动一个 co-shell 实例（同一 workspace / db），查询 `sub_agent_status`。
   - 预期：若子进程已结束 → 该行不得显示为 running（应为 Stale/终态，见 `loadLocked` 的 `processAlive` 判定）；若仍是 running（子进程还活着）→ 记录该现象并参见 UC-0012 的遗留风险。
4. 单测路径：构造 `subAgentMgr == nil` / `io` 不支持起新迭代能力的 Agent，触发完成回调。
   - 预期：回退为"打印 + 动态事件缓存"，不 panic。

## 预期结果

- 无 IO/无进程时通知路径静默降级，不产生崩溃。
- 持久化状态不因通知机制而变得更糟（本用例同时作为"是否遗留 running 幽灵行"的观测点）。

## 验证方式

- 退出后日志无 panic / fatal；重启后 `sub_agent_status` 的状态合理。
- 单元测试补充：`io == nil` 或未实现起新迭代接口时，回调不 panic 且降级分支被覆盖。
