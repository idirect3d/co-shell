# FIX-590 UC-0001：md 增量渲染 + 自适应节流（D1）与输入/输入法期间让路（D2）

> 分支：**FIX-590**　版本：**v0.91.6**　需求：用户 2026-10-03「输入框打字/输入法很慢、输入时 CPU 很高，空闲时也卡」
> 判定口径：markdown 渲染不再「每个动画帧对整段文本重渲染」；**输入/输入法期间让路**（不渲染、不滚动跟随），按键与候选窗口即时响应；**渲染结果与全量渲染逐字节一致**。

## 目的

已实测：`scheduleMd`（app.js:1225-1238）每帧全文重渲染，成本随文本增长（2KB→2.3ms、10KB→2.7ms、50KB→7.8ms、**200KB→29.7ms/帧**），主线程被占满后按键只能排队 → 打字/输入法卡、CPU 高。主输入框自身的每键工作很轻（`autoGrow` 实测 0~1.8ms、无每键网络发送），因此修渲染侧才是治本。

## 变更点（`web/static/app.js`）

| 位置 | 变更 |
|---|---|
| `scheduleMd`（1225-1238） | 改为**增量渲染**（只重渲染本次新增的尾段/脏区，未变前缀不动）+ **按文本长度分档节流**；保留 rAF 合并语义 |
| IME/输入让路 | 新增输入活动标志：`compositionstart` 置位、`compositionend` 后短延时复位（沿用 `__imeJustEnded` 语义）；让路期间跳过 `mdRender` 与 `scrollStream`，结束后**补渲染一次** |
| 强制收尾 | `token_iter` / `done` / 块类型切换（llm↔thinking↔tool）处强制一次完整渲染，保证最终 DOM 与全量一致 |
| 不改动 | `md.js` 的渲染算法、`thinkPinned` 的 pinned 行为、SUP 块与 TOOL 参数块的既有渲染入口 |

## 用例 A：增量渲染与全量渲染等价

- 准备长 markdown（标题/段落/粗体/行内码/列表/表格/围栏代码/链接/路径链接），用两种路径渲染同一最终文本：`mdRender`（全量）与新路径（反复增量追加后收尾）。
- 断言：最终 `innerHTML` **逐字节相等**；`textContent` 相等。

## 用例 B：分档节流

- 阈值（实现固定并在注释中写明）：`≤ 8KB` 每帧渲染；`8KB–64KB` 至少间隔 3 帧；`> 64KB` 至少间隔 10 帧。
- 断言：连发 60 个 chunk（每 chunk 4KB，最终 240KB）时 `mdRender` 调用次数 ≤ 60/10 + 2（收尾一次）。
- 断言：小文本（≤ 8KB）仍每帧渲染（流式观感不退化）。

## 用例 C：输入法期间让路

- `compositionstart` 后连发 20 个 `content_chunk`。
- 断言：期间 `mdRender` 调用数 = 0；`streamB.scrollTop` 不变（未执行 `scrollStream`）；`curLLM.raw` 完整累积（不丢字）。
- `compositionend` 后：断言触发 **1 次**补偿渲染，且结果与全量渲染一致。

## 用例 D：普通输入（无输入法）也让路

- 在 `input` 事件后 300ms 窗口内连发 chunk。
- 断言：让路生效（`mdRender` 计数 0）；按键处理延迟（dispatch → handler 结束）**< 16ms**。

## 用例 E：收尾一致性

- 让路期间触发 `token_iter` 与 `done`。
- 断言：各强制完整渲染一次；DOM 与全量渲染一致；消息可视化（`msgVizPending`）与尾块归属不受影响。

## 用例 F：量化对照（性能）

| 场景 | 改前（实测基准） | 改后断言 |
|---|---|---|
| 200KB 文本连续 60 帧 | ~29.7ms/帧（累计 ≫ 1s） | 累计耗时 **下降 ≥ 70%**；单帧 > 16ms 的帧数 ≤ 3 |
| 打字期间主线程最长阻塞 | 未测 | **< 50ms** |
| 小文本流式（≤8KB） | 每帧 2.3ms | 保持每帧渲染，单帧 ≤ 3ms |
