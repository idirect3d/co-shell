## 一、改前基线（实测）

| 项 | 值 |
|---|---|
| 真实流式 53.6s 的 JS 侧占用 | 0.7% 主线程（`mdRender` 1299 次 / 388.6ms；`markStreaming` 5124 次 / 13.2ms；0 长任务） |
| 20KB 富文本（358 DOM 节点）全量重建 | JS 0.5ms + 强制布局 1.6ms（131 块会话，Chrome） |
| 同一消息，**只重建尾部块** | 强制布局 0.1ms（约 1/10） |
| 会话体量影响（4 块 vs 500 块） | 1.0ms vs 1.2ms → 单次渲染成本**不随会话体量放大** |
| 策略模拟（真实消息，88 chunk/s） | “仅新块渲染”：6.2KB 消息最长画面静止 **3.6s**、56.8KB 长文本 **41s**（不可接受）；“增量渲染”保持 50ms 节奏下总开销 1491ms → **130ms** |

## 二、阶段 1：定位（临时性能 HUD，不修改仓库代码）

HUD 位置：工作区 `tmp/fix596-perfhud.js`（未入库）。用法：在出问题的页面控制台粘贴，跑一段 30~60s 的真实流式后点浮层复制报告。

判定口径：

- **A 可安装**：浮层出现在右上角，逐秒刷新；报告里 `call mdRender/scheduleMd/markStreaming/scrollStream` 无 `MISSING`。
- **B 可定位瓶颈**：报告能给出 ①各函数调用频次与累计耗时 ②`JSON.parse` 频次/耗时/字节数 ③帧间隔 p50/p95/max 与 >33ms 帧数 ④LoAF 的 `scripting` 与 `style+layout` 拆分（Safari 不支持时该行为 0）⑤DOM 节点数与流式块数。
- **C 结论可判定**：若 `mdRender` 累计耗时占比低、而帧间隔 p95 远超 16.7ms 或 LoAF 的 `style+layout` 占主导 → 瓶颈在布局/绘制；若 `JSON.parse` 或其它函数占主导 → 瓶颈在 JS 侧。据此选定阶段 2 的实施方案。

## 三、阶段 2：候选实施方案（待定位结果选定）

- **① 增量渲染（推荐）**：已闭合的块只渲染一次并冻结，只重建正在增长的尾部块；块闭合时立即渲染，尾部块保留 50ms 档节奏。验收：单次渲染成本降至基线约 1/10；打字机效果与现状一致（画面静止窗口 ≤ 现状）；流式结束/切会话后内容与 `mdRender` 全量重建结果**完全一致**（结束时全量兜底）。
- **② 块边界立即渲染 + 尾部 250ms 兜底**：只改 `scheduleMd` 门控。验收：渲染次数降至基线 1/3~1/5；画面静止窗口 ≤251ms。
