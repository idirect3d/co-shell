> 权威依据：`ROADMAP.md` v0.102.3 / FIX-619；分支 **FIX-619**，版本 **v0.102.3**（FIX 走 patch 递增）。
> 调查报告：`work/research/20261007-移动端重连问题/调查报告.md`
> 相关代码：`web/static/app.js`（连接与重连 636-895：`clientID` 644、`reconnectBackoff` 672、`scheduleReconnect` 677、`wsConnect` 688、守卫 689、`onopen` 700、`onclose` 744、`wsDisconnect` 870、连接开关 886；生命周期 1547-1551）、`web/server.go`（`handleWS` 817）、`web/ws.go`（ping/pong 225-240、写超时 272-278）。

> 问题（用户实测，2026-10-07 14:17）：移动端长时间不在线后重新连接连不上；点 iOS 导航栏刷新按钮无效并弹「请求超时 / 无法连接」；完全关闭 App 重启后可连。
> 根因（三层，详见调查报告）：① iOS 刷新只有 `webView.reload()`；② `app.js:689` 的 OPEN 守卫把移动网络下「收不到 onclose 的僵尸套接字」当成健康连接 → 永不重连，且无心跳、无生命周期兜底；③ 服务端无主动 ping、无读超时。

> 已确认决策（用户确认，不可改动）：
> ① 方案范围 = **E + B + A + C** 全量，实施顺序 **E→B→A→C**；
> ② 版本归属 **v0.102.3**，任务号 **FIX-619**；
> ③ iOS 端同时出包并上传 TestFlight/直装。

> 本次涉及的参数（可调但需在用例中保持一致）：心跳发送间隔 `25s`、看门狗判定阈值 `45s`、看门狗检查间隔 `10s`、服务端 ping 间隔 `30s`、服务端读超时 `90s`、iOS 加载超时 `15s`、iOS 失败重试退避 `1s/3s/5s`。

## 实现要点（预期，供编码时对齐）

`web/static/app.js`：
1. 新增常量 `WS_HEARTBEAT_MS = 25000`、`WS_WATCHDOG_MS = 45000`、`WS_WATCHDOG_TICK_MS = 10000`；
2. 连接建立后启动心跳定时器：`wsSend({type:"ping"})`；收到任意帧刷新 `lastMsgAt`；
3. 看门狗 tick：`wsReady && Date.now() - lastMsgAt > WS_WATCHDOG_MS` → `forceReconnect()`（置 `ws = null; wsReady = false;` 后 `reconnectAttempt = 0; wsConnect();`）；
4. `wsConnect()` 守卫调整为：`OPEN` 且 `now - lastMsgAt <= WS_WATCHDOG_MS` 才 return；
5. 生命周期：`visibilitychange`（visible）/`pageshow`/`online`/`focus` → `ensureConnected()`：非 OPEN 立即重连（重置退避）；OPEN 但超阈值 → `forceReconnect()`；
6. 手动断开（`manualClose = true`）时，心跳与生命周期均不得触发重连。

服务端无需为 ping 新增业务分支：`ping` 帧由 `dispatch` 静默忽略（若实现为协议层 ping 则天然不进入业务层）。

## 用例详情

### A. 静态断言（建议落在 `web/fix619_test.go`，读 `static/app.js` 文本）

- **A-001**：断言存在心跳间隔常量（值含 `25000`）与发送语句（`type: "ping"` 或 `"ping"`），且发送位于连接建立后的定时器回调中。
- **A-002**：断言存在看门狗阈值常量（`45000`）与「超阈值 → 强制重连」分支（`forceReconnect` 或等价的 `ws = null` + `wsConnect()` 组合）。
- **A-003**：断言 `wsConnect()` 的守卫条件中同时引用了 `lastMsgAt`（即不再是单纯的 `readyState === OPEN` 短路）。
- **A-004**：断言 `visibilitychange`、`pageshow`、`online`、`focus` 四个事件名均出现，且回调内调用连接检查函数。
- **A-005**：断言 `onmessage` 回调（或统一入口）中更新 `lastMsgAt`。
- **A-006**：断言 `mobile/ios/Runner/WebViewController.swift` 中出现 `os_log`（或 `Logger`）调用，且 `didFail` / `didFailProvisionalNavigation` / `didFinish` 三个方法体内至少各有一条记录调用，日志内容包含 URL 与 error domain/code 字段。

### B. 运行时用例（Node + DOM shim 脚本，注入真实 `app.js` 逻辑）

> 做法沿用 FIX-604 的既有模式：以最小 DOM shim 加载 `web/static/app.js`，用假 `WebSocket` 类与假定时器（可手动推进时间）驱动，断言连接行为。

- **B-001 僵尸 socket 强制重连**
  - 步骤：建立连接（假 socket `readyState = OPEN`）→ 手动推进时间 46s 且期间不投递任何消息 → 触发一次看门狗 tick。
  - 断言：旧 socket 被 `close()`；`new WebSocket` 被再次调用（计数 +1）；新连接 `onopen` 后 `connText` 恢复为「已连接」。
- **B-002 回前台立即重连**
  - 步骤：将 socket 置为 `CLOSED`（`wsReady=false`）→ 派发 `visibilitychange`（`document.hidden=false`）。
  - 断言：立即调用 `new WebSocket`（不等待退避时间）。
- **B-003 网络恢复立即重连**
  - 步骤：`manualClose=false`、socket 非 OPEN → 派发 `online`。
  - 断言：立即新建连接。
- **B-004 健康连接不被误杀**
  - 步骤：连接后每 20s 投递一条任意服务端消息（或 pong），连续推进 120s。
  - 断言：`new WebSocket` 计数保持 1；无 `close()` 调用。
- **B-005 手动断开不被复活**
  - 步骤：调用 `wsDisconnect()`（或点击连接开关）→ 推进时间 120s → 派发 `visibilitychange`(visible)、`online`、`focus`。
  - 断言：`new WebSocket` 计数不增加（保持断开态）。
- **B-006 退避重连回归**
  - 步骤：连接后触发 `onclose`（非手动断开）→ 检查退避序列。
  - 断言：按 1s/2s/5s/10s/20s/30s 递增，成功连接后 `reconnectAttempt` 归零。
- **C-001 服务端接受心跳帧（Go 用例）**
  - 步骤：真实 WS 连接（复用 `web/ws_test.go` 的 `dialWSPath`）→ 发送 `{"type":"ping"}`。
  - 断言：连接不被关闭；随后既有指令（如 `mode_get`）仍正常返回（证明 ping 无副作用）；如实现为协议层 ping/pong，则断言服务端回 pong。
