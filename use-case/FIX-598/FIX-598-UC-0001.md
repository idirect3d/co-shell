# FIX-598 UC-0001：LLM 错误按成因分类——仅格式类错误才移除上下文

> 分支：**FIX-596**（会话分支，任务编号 FIX-598）　版本：**v0.92.2**　BUILD：**1205**
> 判定口径：`dial tcp ... i/o timeout` 这类网络/服务端/认证/限流错误**不再移除任何消息**，只做有界重试或直接终止；仅"消息格式不合法"类错误保留原有"移除最后一个 assistant(tool_calls) 及后续消息"的行为。

## 背景（改前基线，代码证据）

`agent/run_stream.go`（流式错误分支）在删除动作**之前不区分错误类型**，唯一依据是 `removedContent != ""`——即"历史里能否从后往前找到一条带 `tool_calls` 的 assistant 消息"（`agent/agent.go:2314`，全量回溯）。因此：

- 纯网络故障（`i/o timeout`、`connection reset`）只要历史里有工具调用，就会**删掉合法的 assistant+工具结果**并反复重试（直到 `context-remove-limit` 或 `error-max-single-count`）。
- 分类器 `classifyConnectionError`（`problem_solver.go:218`）虽已存在，但**调用点（`run_stream.go:875`）在删除动作之后**，且只承认 HTTP 401/403/404/429/5xx 与少量关键字，网络类错误一律落入"模糊"。
- `llm` 客户端零重试（`client.go`：非流式有 `httpClient.Timeout`，流式靠 context），一次抖动即直达上述删除路径。

**危害**：模型丢失"刚调过什么工具/拿到什么结果"的记忆 → 可能重复执行有副作用的工具；删掉的内容又被回灌进 user 消息（`KeyLLMErrorFeedbackRef`）并附"请修正后重试"，对网络故障无意义。

## 用例与结果

- **A 分类正确性** → ✅ 12 组用例：`nil`→unknown；`*url.Error`/`context.DeadlineExceeded`/`connection reset` 文本→network；`context.Canceled`→unknown（不重试）；401/404→auth；429→rate-limit；503→server；含 `tool_calls` 文案的 400→context-format；`maximum context length`→context-too-long；其它 400→unknown。
- **B 仅格式类可删上下文（主判定）** → ✅ network/auth/rate-limit/server/unknown 五类 `AllowsContextRemoval()==false`；context-format/context-too-long 为 `true`（保留原行为）。
- **C 可重试性与预算** → ✅ 仅 network/rate-limit/server 可重试；连续 3 次允许、第 4 次拒绝；调用成功后预算复位。
- **D 退避与取消** → ✅ 1s→2s→4s→8s（封顶）；`ctx` 取消时 `sleepCtx` 立即返回 false（不睡满退避）。
- **E 编译与静态检查** → ✅ `go build ./... && go vet ./...` 通过。
- **F 回归** → ✅ `agent` 包新用例全绿；主模块 `-short` 的失败集与改动前一致（`agent` 两例语言环境相关、`i18n` 三例为 `.rules/` 说明文案既有失败），均与本次改动无关（`grep` 确认失败断言与新增 key 无交集）。
