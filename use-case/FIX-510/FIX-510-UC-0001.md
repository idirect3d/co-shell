# FIX-510 测试用例 — 超限时豁免 reorganize_context / attempt_completion 与移除必需 meta

> 分支：FIX-510
> 版本：v0.51.1
> 关联任务：FIX-510
> 关联缺陷：FEATURE-264（超限跳过工具执行）、FIX-318（重组后折叠历史）、FEATURE-450（meta 校验）

## 背景

上下文占用超过 `context-reorganize-threshold` 时，`agent/run_stream.go` 会置
`reorganizePending=true`，跳过本轮**全部**工具执行并向 LLM 回灌"立即整理上下文"指令。
该分支存在两处缺陷，导致 `reorganize_context` 几乎无法一次调用成功：

1. **豁免名单不完整（主因）**
   - 现有豁免判定 `hasReorganizeCall` 只识别 `reorganize_context`；`attempt_completion`
     （报告完成）会被一并跳过，任务收尾被无限推迟。
   - 更关键的是：豁免判定依赖"本轮 toolCalls 中是否出现 `reorganize_context`"。当 LLM
     首次输出 `reorganize_context` 时，若该轮因其它原因未进入该分支（例如同时携带其它
     工具、或首轮被跳过），用户看到的就是"上下文超限，已跳过此轮工具执行"——即首次调用
     不生效。

2. **`reorganize_context` 仍把 `meta` 声明为必需参数（叠加因）**
   - `agent/tools.go` 中 `reorganize_context` 的 `required` 含 `"meta"`，`risk.go` 的
     `toolRequiresMeta` 据此对它执行 `assessRisk` 强校验（`risk` 必填且必须为
     low/medium/high 之一）。
   - 一旦 meta 缺失或 `risk` 取值非法，工具被 `skipExec` 判失败 —— 在上下文超限这一
     最需要重组的时刻，多输出一段 meta 恰恰放大了首次调用失败的概率。
   - 对照：`track_task_progress` 的 `required` 已不含 meta（`tools.go`），`risk.go` 注释
     亦称 attempt_completion 不再声明 meta —— 注释与代码不一致。

## 修复方案

1. **豁免集合扩展**：把"超限时豁免的工具"从仅 `reorganize_context` 扩展为
   `reorganize_context` + `attempt_completion`。判定语义保持现有"整轮豁免"（只要本轮
   toolCalls 含豁免工具，则该轮工具照常执行，不再跳过并回灌紧急指令）。
2. **移除必需 meta**：`reorganize_context` 的 `required` 去掉 `"meta"`（`properties` 中
   的描述保留，LLM 仍可选提供），使其不再受 `assessRisk` 校验约束。
3. **注释对齐**：修正 `risk.go` 中与代码不符的说明。

## 运行时用例

### UC-0001 超限时首次调用 reorganize_context 被执行（核心回归）

**前置条件**
- 启动 `co-shell --serve --port <port>`（测试 Web UI 必须带 `--serve`）。
- 配置满足：`context-policy = reorganize`、`context-reorganize-threshold = 80`、
  模型 max context length 已知（使当前迭代 token 占比可超过阈值）。
- 造一个超限会话：持续进行长输出轮次，直到状态栏 token 占比 ≥ 80%。

**步骤**
1. 在超限状态下，向 LLM 提出继续推进任务的需求（不主动提示它整理上下文）。
2. 观察 LLM 第一次输出 `reorganize_context` 调用的那一轮。
3. 检查事件流与本轮工具执行结果。

**预期结果**
- **不再出现**"上下文超限 (x% > 80%)，已跳过此轮工具执行"阻断 `reorganize_context`。
- `reorganize_context` 被真正执行：界面出现"✅ 上下文已重新整理：摘要 N 字符。"。
- 历史被折叠为 `[system, user(summary)]`，后续轮次上下文占用显著下降。
- 修复前：首次调用被跳过，只能靠回灌的紧急指令在下一轮重试；修复后：**首次即生效**。

**验证要点**
- 日志中 `Agent.RunStream: context usage ... skipping tool calls` 不应出现在该轮。
- 折叠日志 `Agent.collapseAfterReorganize: collapsed history to 2 messages` 出现。

---

### UC-0002 超限时 attempt_completion 被执行，任务正常收尾

**前置条件**
- 同 UC-0001，会话处于超限状态（token 占比 ≥ 阈值）。
- 任务实际已完成，LLM 准备报告完成。

**步骤**
1. 让 LLM 调用 `attempt_completion` 提交结果。
2. 观察该轮是否被"跳过工具执行"拦截。

**预期结果**
- `attempt_completion` **不再被跳过**：界面显示完成结果与 `session_title`。
- 任务正常进入完成确认流程，而不是被迫先整理上下文再重述结果。
- 未出现该轮所有工具均被忽略的告警。

**验证要点**
- 修复前：`attempt_completion` 被跳过，用户看不到完成信息，任务被延长。
- 修复后：当轮即完成。

---

### UC-0003 超限时普通工具仍被跳过（回归保护）

**前置条件**
- 同 UC-0001，会话处于超限状态。
- LLM 本轮只调用普通工具（如 `read_file` / `execute_command` / `search_files`）。

**步骤**
1. 在超限状态下，让 LLM 输出一个普通工具调用。
2. 观察工具是否执行。

**预期结果**
- 普通工具**仍按原逻辑被跳过**，界面出现"上下文超限 (x% > y%)，已跳过此轮工具执行"。
- 收到"你必须马上进行上下文整理…立即调用 reorganize_context 工具"的紧急指令。
- 即：豁免仅对 `reorganize_context` / `attempt_completion` 生效，未放宽其它工具。

---

### UC-0004 超限时本轮混合调用（豁免工具 + 普通工具）——整轮执行

**前置条件**
- 同 UC-0001，会话处于超限状态。

**步骤**
1. 构造 LLM 在同一轮内同时调用 `reorganize_context` 与一个普通工具
   （可通过提示词诱导，XML 模式下同一响应内含两个工具标签）。
2. 观察整轮工具的执行情况。

**预期结果**
- 由于本轮含豁免工具，**整轮工具均被执行**（保持现有 `hasReorganizeCall` 的"整轮豁免"语义，
  避免出现"assistant 记录了 N 个 tool_calls 但只有部分 tool 结果"导致 API 400）。
- 普通工具的结果照常回灌；`reorganize_context` 的摘要折叠在全部工具结果追加后执行
  （FIX-318 行为不变）。

**说明**
- 本用例固化"整轮豁免"语义。若后续改为"逐个工具豁免"，必须同步为被跳过的工具补齐
  "因超限被跳过"的结果消息，否则违反 OpenAI 的 tool_calls/tool 配对约束。

---

### UC-0005 reorganize_context 不带 meta 仍成功执行

**前置条件**
- 超限或未超限均可；建议在超限状态下验证（最贴近真实场景）。

**步骤**
1. 让 LLM 调用 `reorganize_context`，**只提供 `summary_prompt`，不提供 `meta`**。
2. 观察工具是否执行成功。

**预期结果**
- 工具正常执行，输出"✅ 上下文已重新整理：摘要 N 字符。"。
- **不出现** meta 校验类错误（如 `missing required risk field`）。
- 上下文按摘要折叠。

**验证要点**
- 修复前：因 `required` 含 meta，`toolRequiresMeta` 为 true → `assessRisk` 报错 → `skipExec`。
- 修复后：`toolRequiresMeta(reorganize_context) == false`，校验被跳过。

---

### UC-0006 reorganize_context 携带非法 meta 仍成功执行

**前置条件**
- 同 UC-0005。

**步骤**
1. 让 LLM 调用 `reorganize_context`，并故意给出非法 meta
   （例如 `risk` 取值 `"unknown"`、或 `risk_reason` 为空）。
2. 观察工具是否执行成功。

**预期结果**
- 工具**仍成功执行**，不因 meta 非法被拦截。
- 上下文正常折叠。

**说明**
- 这是"关键恢复手段不应被元数据格式问题阻断"的显式验证。

---

### UC-0007 连续多轮超限，每轮 reorganize_context 均被放行

**前置条件**
- 同 UC-0001；上下文体量足够大，使得整理后仍可能再次超限（或人为把阈值调低复现）。

**步骤**
1. 在超限状态下连续触发 3 轮 reorganize_context。
2. 记录每轮是否被放行。

**预期结果**
- 每一轮 `reorganize_context` 都被执行，无一轮被"跳过工具执行"拦截。
- 每次折叠后 messagePointer 与 needAdjustPointer 正确重置，无历史残留导致的重复折叠。

---

### UC-0008 未超限时行为不变（回归保护）

**前置条件**
- 会话 token 占比**低于**阈值。

**步骤**
1. 正常调用 `reorganize_context`（可带可不带 meta）与 `attempt_completion`。
2. 调用普通工具。

**预期结果**
- 三者均正常执行，与修复前一致。
- 未引入额外的跳过或校验行为。

## 单元测试用例

### UC-0009 toolRequiresMeta(reorganize_context) == false

- 构造 Agent（含完整工具集），断言 `toolRequiresMeta("reorganize_context") == false`。
- 同时断言 `toolRequiresMeta("read_file") == true`（对照组，证明确有工具仍要求 meta）。

### UC-0010 豁免判定对两类豁免工具均为 true

- 新增/复用超限豁免判定函数，输入：
  - `[reorganize_context]` → 豁免
  - `[attempt_completion]` → 豁免
  - `[read_file]` → 不豁免
  - `[]`（空）→ 不豁免
  - `[read_file, reorganize_context]` → 豁免（整轮豁免语义）
  - `[read_file, attempt_completion]` → 豁免

## 提示词层用例

### UC-0011 XML 模式 meta 说明包含“不需要 meta 的工具”清单

**前置条件**
- `tool-call-mode = xml`、`intent-exposure` 开启（meta 说明才会被注入）。

**步骤**
1. 构建系统提示词（或直接调用 `buildXMLToolPrompt`）。
2. 在“工具调用透明化（meta 对象）”一节中查找免 meta 清单。

**预期结果**
- meta 说明中出现一行列出**不需要 meta 的工具**（应包含 `reorganize_context`，且**不包含** `read_file`）。
- 文本中**不再残留** `{NO_META_TOOLS}` 占位符。
- 清单由工具 schema 实时生成（与 `toolRequiresMeta` 同源），不随条件启用的工具集腐化。

**说明**
- OpenAI 模式**不输出**该文本清单：工具以 JSON schema 下发，`required` 列表对模型直接可见，无需再以文本重复。因此 `KeySystemPromptToolUsageMetaOpenAI` 不含占位符。
- 当 `intent-exposure` 关闭时，meta 说明整段不注入，占位符随之消失，也不会残留。

### UC-0012 i18n 模板与占位符

- `KeySystemPromptToolUsageMetaXML`（中/英）必须包含 `{NO_META_TOOLS}`。
- `KeySystemPromptToolUsageMetaOpenAI`（中/英）**不得**包含 `{NO_META_TOOLS}`。
- `KeySystemPromptMetaExemptTools`（中/英）必须包含 `%s` 占位符以接受工具清单。

### UC-0013 超限放行时不输出「已跳过此轮工具执行」警告（回归）

**前置条件**
- `context-policy = reorganize`、`context-reorganize-threshold` 设为容易触发的值（如 25%）。
- 在上下文已超限（如 26% > 25%）时，让 LLM 调用 `attempt_completion`（或 `reorganize_context`）。

**步骤**
1. 观察该轮事件流中的 SYS 信息块。
2. 确认工具是否实际执行。

**预期结果**
- 工具**正常执行**（`attempt_completion` 正常报告完成；`reorganize_context` 正常折叠上下文）。
- 界面**不出现**「上下文超限 (x% > y%)，已跳过此轮工具执行」警告块。
- 也**不出现**问题模型（problem solver）针对本次超限的分类/终止提示。
- 仅在后端日志中记录一条 info（本轮因携带豁免工具而继续执行）。

**验收要点**
- 修复前：工具放行了，但警告先于豁免判定发出 → 用户看到自相矛盾的提示。
- 修复后：“是否跳过”与“是否告警/咨询问题模型”由同一判定 `contextOverflowSkipsTools()` 决定，不可能不一致。

**对照场景（不可放宽）**
- 超限且本轮仅调用普通工具（如 `read_file`）→ 仍应输出“已跳过此轮工具执行”警告，并追加“必须马上整理上下文”的紧急指令。
