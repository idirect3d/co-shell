# FIX-511 测试用例 — 页面刷新 / 重连后运行状态同步与断连语义

> 分支：FIX-511
> 版本：v0.51.2
> 关联任务：FIX-511
> 关联特性/缺陷：FEATURE-369（合并发送/中断按钮）、FEATURE-425 / FIX-426（运行态呼吸效果）、FEATURE-458（连接控件为连接/断开切换）、FEATURE-499（agent busy 状态与 /api/status）、FEATURE-507（刷新后历史回放）

## 背景

运行态的界面表现（co-shell logo 呼吸、发送/中断按钮的红色边框 ⏸ 态、会话标题高亮点呼吸）完全由前端 `setRunning()` 驱动，而它只接收实时 WebSocket 事件：

- `turn_start` → `setRunning(true)`
- `await_input` → `setRunning(false)`

这两条事件由 `WebSession.ReadLine` 直接 `srv.sendEvent` 发出（`web/session.go`），**不经过渲染器**，因此不会走 `r.coalescer.Add(ev)` → `AppendEvent` 的持久化路径（`web/session.go`）。结果是：

1. **刷新后运行态丢失**：历史回放里没有 turn 边界事件；且 `ws.onopen` 只请求 mode / session / yolo / history，从不查询当前运行态，于是 `boot()` 的 `setRunning(false)` 一直生效 —— 后端在跑、界面显示空闲。
2. **断开后仍渲染在途消息**：`ws.onmessage` 没有任何连接态或套接字归属校验，点击"断开连接"后，已进入浏览器任务队列（或 CLOSING 握手期间）的消息仍会被 `renderEvent` 渲染。
3. **旧套接字回调污染新连接**：`ws.onclose` 同样未校验归属，快速"断开 → 重连"时旧连接的回调会把新连接的 `wsReady` 置为 false 并将状态重置为空闲，抹掉刚同步好的运行态。
4. **重连重复回放**：`renderHistory` 的非 prepend 分支只追加不清空，而无游标的 `history_get` 只在 `ws.onopen` 发出 → 未刷新页面仅重连时，最近一页消息会被重复追加。

后端其实一直持有该状态：`agent.IsBusy()`（`RunStream` 进入 `SetBusy(true)`、退出 `SetBusy(false)`）已注入服务端 `busyFn`，并暴露为 `GET /api/status`；连接时也已有状态快照通道 `handleWS` → `sendState`（`kind:"state"`，当前只携带任务计划）。

## 修复方案

1. **复用连接时状态快照（主修复）**：`sendState` 在既有的 `kind:"state"` 消息中附带 `busy`（取自 `busyFn`，即 `agent.IsBusy()`）；前端在 `state` 分支调用 `setRunning(busy)`。服务端在**每次**连接建立时推送该快照，因此页面刷新与点击"重新连接"都能立即恢复运行态。
2. **断开即停止接收**：`ws.onmessage` 增加守卫 —— 未处于已连接状态、或消息来自非当前套接字时直接丢弃。
3. **套接字归属校验**：`onopen` / `onmessage` / `onclose` 绑定到本次连接自己的套接字实例，旧套接字的回调不再改写新连接的状态。
4. **重连重建视图**：初始页（无游标）历史回放前清空事件流，使重连表现为"重新同步"而不是"重复追加"。

## 运行时用例

### UC-0001 任务运行中刷新页面 → 运行态外观恢复（核心回归）

**前置条件**
- 启动 `co-shell --serve --port <port>`（测试 Web UI 必须带 `--serve`，避免自动打开的系统浏览器占用单客户端连接）。
- 浏览器打开页面，确认连接控件显示"已连接"。

**步骤**
1. 发送一个耗时较长的任务（例如让 Agent 连续执行多个工具调用，或明确要求多轮推进）。
2. 在任务**运行中**（按钮显示 ⏸）刷新页面（F5）。
3. 等待页面加载完成、连接恢复。
4. 检查运行态外观：
   - `#logo` 是否具有 `breathing` 类；
   - `#sendBtn` 的文本是否为 `⏸`、是否具有 `run` 类、标题是否为"中断"；
   - `#streamActive` 是否具有 `breathing` 类。

**期望结果**
- 上述三项全部与后端一致：logo 呼吸、按钮为红色边框的 ⏸、会话标题高亮点呼吸。
- 状态在刷新完成后立即恢复，无需等待下一次 turn 边界事件。

**验证命令（DevTools Console）**
```js
JSON.stringify({
  logo: document.getElementById("logo")?.classList.contains("breathing"),
  active: document.getElementById("streamActive")?.classList.contains("breathing"),
  btnText: document.getElementById("sendBtn")?.textContent,
  btnRun: document.getElementById("sendBtn")?.classList.contains("run"),
})
```
期望：`{"logo":true,"active":true,"btnText":"⏸","btnRun":true}`

**修复前表现**：`{"logo":false,"active":false,"btnText":"▶","btnRun":false}`（缺陷复现）。

### UC-0002 空闲时刷新页面 → 不得误显运行态（对照）

**前置条件**：任务已结束，界面停在等待输入状态。

**步骤**
1. 确认按钮显示 ▶、logo 无呼吸效果。
2. 刷新页面。
3. 再次检查运行态外观。

**期望结果**：刷新后仍为空闲态（`logo=false`、`active=false`、`btnText=▶`、`btnRun=false`），不得因快照同步而误显运行态。

---

### UC-0003 任务运行中"断开 → 重新连接" → 恢复运行态外观

**前置条件**：同 UC-0001，任务处于运行中。

**步骤**
1. 点击连接控件切换为"断开连接"。
2. 确认控件显示"未连接"。
3. 再次点击控件切换回"已连接"。
4. 等待连接建立后检查运行态外观（同 UC-0001 的三项）。

**期望结果**
- 重连成功后运行态外观立即恢复（logo 呼吸 / ⏸ + run / 标题高亮点呼吸），与后端 `GET /api/status` 的 `busy` 一致。
- 不出现"已连接但界面显示空闲"或"未连接"的错误显示。

---

### UC-0004 点击"断开连接"后在途消息不再渲染（断开即冻结）

**前置条件**：任务处于运行中且事件流持续输出（例如工具连续执行、LLM 持续流式输出）。

**步骤**
1. 记录当前事件流中 `.ev` 块的数量。
2. 点击"断开连接"。
3. 立即持续观察 10 秒，再次统计 `.ev` 块数量与流末尾内容。

**期望结果**
- 点击断开后事件流不再新增内容（块数量不再变化），不再出现新的流式文本/工具块（即使后端仍在运行、服务端队列中仍有在途消息）。
- 页面不因丢弃消息而报错（Console 无异常）。

**验证命令**
```js
document.querySelectorAll(".ev").length
```

---

### UC-0005 快速"断开 → 重连" → 连接状态与运行态不被旧套接字回调污染

**前置条件**：任务处于运行中。

**步骤**
1. 点击"断开连接"，随后在 1 秒内再次点击以重新连接。
2. 等待 3 秒（确保旧套接字的 `onclose` 回调已触发）。
3. 检查连接控件文案、运行态外观与 `running` 语义是否仍为"已连接 + 运行中"。

**期望结果**
- 控件保持"已连接"，运行态外观保持呼吸 + ⏸（不被旧连接的回调重置为空闲/未连接）。
- 后续事件正常接收。

---

### UC-0006 重连后事件流不出现重复消息（回放重建而非追加）

**前置条件**：事件流中已有若干消息（建议 ≥ 3 个消息块），任务可处于空闲或运行中。

**步骤**
1. 记录重连前的事件流内容特征（块数量、各块标题/首行文本）。
2. 点击"断开连接"，再点击"重新连接"。
3. 等待历史回放完成，统计事件流块数量，并检查是否出现重复的相同消息。

**期望结果**
- 事件流被重建为后端持久化的最近一页内容，**不出现重复块**（同一消息只出现一次）。
- 视图滚动到最新消息处。

**修复前表现**：重连后最近一页消息被再次追加，出现重复块。

---

### UC-0007 重连后新消息继续正常接收（回归保护）

**步骤**
1. 断开连接后重新连接。
2. 发送一条新输入（例如"回复 ok"）。
3. 观察事件流与运行态。

**期望结果**：新输入被正常发送，事件正常渲染，运行态随 turn 边界正确切换（发送后为 ⏸，任务结束后回到 ▶）。

### UC-0008 交互等待（ask / interaction）中刷新 → 仍显示运行态

**前置条件**：触发一个需要用户作答的交互（例如 Agent 调用询问类工具，或需要确认的操作）。

**步骤**
1. 在交互等待期间（Agent 阻塞等待用户回答、`RunStream` 仍在执行中）刷新页面。
2. 检查运行态外观。

**期望结果**：仍显示运行态（busy 为真），与后端一致（不因"等待输入"而与 `await_input` 语义混淆）。

### UC-0009 等待输入（await_input）后刷新 → 显示空闲态

**前置条件**：一轮任务已完成，REPL 处于等待用户输入状态。

**步骤**
1. 确认按钮为 ▶、logo 无呼吸效果。
2. 刷新页面。
3. 检查运行态外观。

**期望结果**：显示空闲态，不得误显运行态（验证快照的 busy 与 turn 边界语义一致）。

## 单元测试用例

### UC-0010 sendState 携带 busy：busyFn 为 true / false / nil 三种情况

**测试目标**：`web` 包中连接时状态快照的构造逻辑。

**步骤与期望**
1. `SetBusyProvider` 注入返回 `true` 的提供者 → 构造的 `kind:"state"` 消息 JSON 中 `busy` 为 `true`。
2. 注入返回 `false` 的提供者 → `busy` 为 `false`。
3. 不注入提供者（`busyFn == nil`）→ `busy` 为 `false`（不得因 nil 而 panic）。

### UC-0011 无 plan 且无 busy 提供者时 state 消息仍可正常序列化（兼容性）

**测试目标**：快照消息序列化与既有字段兼容。

**步骤与期望**
1. `planFn == nil`、`busyFn == nil` → `state` 消息中 `plan` 为 `null`、`busy` 为 `false`，序列化无错误。
2. 既有 `plan` 字段语义不变（提供者返回非空 JSON 时原样透传）。

## 验收标准汇总

1. UC-0001 / UC-0003：运行中刷新与重连都能恢复运行态外观（logo 呼吸、红色 ⏸、标题高亮点呼吸）。
2. UC-0002 / UC-0009：空闲态与等待输入态不得误显运行态。
3. UC-0004：断开后不再接收/渲染任何消息。
4. UC-0005：快速断开重连不受旧套接字回调影响。
5. UC-0006 / UC-0007：重连重建事件流不重复，且后续消息正常接收。
6. UC-0010 / UC-0011：单元测试通过。
7. `go build ./... && go vet ./...` 与 `go test ./...` 通过。
