# FIX-575 UC-0002：无结果事件的工具调用之后，后续调用仍各自成块

> 分支：**FIX-575**　版本：**v0.85.3**　对应验收标准：**§2**
> 这是原始缺陷的**直接触发路径**：`task_progress` / `attempt_completion` / 空结果工具不产生 `PhaseResult` 事件，回放时前一块 `hasResult` 恒为 false，
> 旧启发式 `fresh = !curTool || curTool.hasResult` 与 `!curTool.raw` 组合导致后续工具调用被并入或被丢弃。

## 目的

验证“工具 A 无结果事件 → 工具 B → 工具 C”这条链在恢复后仍然 **A/B/C 三块齐全**。

## 前置条件

- 同 UC-0001 的启动方式（`--serve --port 28256`）。
- 需要一轮内出现“无结果事件”的工具调用，可用提示词：
  `请新建一个 3 步任务计划，然后用 track_task_progress 上报第 1 步完成，再读取 go.mod 的第 1-5 行，最后用 attempt_completion 结束。`
- 兜底（若模型未按预期编排）：手工先调用一次 `track_task_progress`，紧接着调用一次 `read_file`，观察两者是否**各自成块**。

## 步骤

1. 发送提示词，等本轮结束。
2. 执行 UC-0001 的**脚本 A**（实时基线）。
3. 刷新页面 / 重启服务（`--serve` 进程重启，端口不变），重新打开同一会话并等待回放完成。
4. 再次执行脚本 A。
5. 逐个点开每个 TOOL 块，确认参数区内容归属正确（`path` / `steps` 不串块）。

## 预期结果

| 断言 | 期望 |
|------|------|
| B1 | `track_task_progress` 之后的 `read_file` **自成一块**，不是被并进 `track_task_progress` 块 |
| B2 | `attempt_completion` 之前的工具调用**保持成块**，不被吞掉 |
| B3 | 回放 `toolCount` == 实时 `toolCount`，且 `heads` 顺序一致 |
| B4 | 每个块参数区文本非空且为该工具自身参数（无反串） |
| B5 | 连续两次刷新，结果稳定一致（非“随机缺失”） |

## 修复前失败现象（基线）

- `track_task_progress`（无结果事件）之后的 `read_file` 参数被并入前者块内，该次调用**不再成块**；
- 若前一块 `raw` 为空且 `hasResult=false`，文本走 input 分支但 `fresh=false` → **整段文本被丢弃**；
- 现象随机：取决于中间是否恰好有结果事件，故“散落中间、成块随机缺失”。
