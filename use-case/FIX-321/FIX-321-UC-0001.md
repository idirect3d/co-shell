# FIX-321: 循环反馈消息补全 environment_details + retry_count 重试计数机制

## 背景

当前循环干预产生的 user 消息（两处注入点）只有纯文本 feedback，缺失其他 user 消息普遍具备的 `<environment_details>` 块：

1. `run_stream.go` sync 循环分支（`loopDetectCrit`）：`a.messages = append(a.messages, llm.Message{Role: "user", Content: loopFeedback})`
2. `loop.go` `applyLoopIntervention()`：同样的纯文本 append

结果：LLM 在收到循环反馈时看不到当前时间、cwd、文件列表、任务计划等环境上下文，与其他 user 消息格式不一致。

另外，当前每次循环都追加新 user 消息，多次循环导致历史膨胀。

## 修复方案

### 消息标记（env 内部标签）

```
<environment_details>
  <time>...</time>
  <loop_feedback>true</loop_feedback>     ← 标记该消息是系统生成的循环反馈
  <retry_count>N</retry_count>            ← 当前循环链的重试次数
  ...
</environment_details>
```

### 每次循环干预的判定（扫描最后一个 user 消息的 env）

| 状态 | prompt 方式 | retry / temperature 方式 |
|---|---|---|
| 计数在 feedback 消息上（带 loop_feedback 标记） | 替换 feedback 文本，计数+1 | 计数+1，feedback 文本保留 |
| 计数在用户/工具消息上（有 retry_count 无标记） | 新增 feedback 消息（计数=1），不动原消息 | 计数+1，原提示词不动 |
| 无计数块 | 新增 feedback 消息（计数=1，含 env） | 在最后 user 消息 env 追加计数=1（无 env 先补 env） |

### 核心原则

- 计数只存在于消息上下文中，不设 Agent 状态字段、无归零逻辑
- prompt 方式绝不覆盖真实用户消息（仅在 feedback 消息上替换）
- retry/temperature 方式不新增消息，只在最后 user 消息 env 上追加/更新计数
- judgeLoop 自身发给 judge 模型的 user 消息（独立判定上下文）不在本次改动范围

## 用例列表

### UC-0001 prompt 首次触发：新增带 env 的 feedback 消息（单测）

**前置条件**：循环干预策略为 `prompt`，最后一个 user 消息无 retry_count。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env), assistant(循环内容)]`
2. 调用循环干预逻辑（prompt 方式，feedback 文本="请换个思路"）

**预期**：
- `a.messages` 末尾新增一条 user 消息
- 新消息 ContentParts 为 2 段：`[0]`="请换个思路"，`[1]`=`<environment_details>` 且含 `<loop_feedback>true</loop_feedback>` 与 `<retry_count>1</retry_count>`
- 原真实 user 消息文本与 env 未被修改

### UC-0002 prompt 再次触发：替换已有 feedback 消息文本，不新增消息（单测）

**前置条件**：循环干预策略为 `prompt`，最后一个 user 消息是 feedback 消息（带 loop_feedback 标记 + retry_count=1）。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env), assistant(循环内容), user(feedback 消息, retry_count=1)]`
2. 再次调用循环干预逻辑（prompt 方式，feedback 文本="请换个思路（更具体）"）

**预期**：
- `a.messages` **长度不变**（不新增消息）
- 最后一条 user 消息的 `[0]` 文本更新为"请换个思路（更具体）"
- env 中 `<retry_count>` 从 1 更新为 2
- `<loop_feedback>true</loop_feedback>` 保留

### UC-0003 prompt 遇到用户消息上已有计数：新增 feedback 消息，不动用户消息（单测）

**前置条件**：循环干预策略为 `prompt`，最后一个 user 消息带 retry_count=2（此前 retry 方式加的）但无 loop_feedback 标记。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env 含 retry_count=2), assistant(循环内容)]`
2. 调用循环干预逻辑（prompt 方式）

**预期**：
- `a.messages` 末尾新增一条 user 消息
- 新消息为 feedback 消息（`[1]` 含 `<loop_feedback>true</loop_feedback>` + `<retry_count>1</retry_count>`）
- 原 user 消息的 retry_count=2 保留不动（用户消息不被覆盖）

### UC-0004 retry 首次触发：在最后 user 消息 env 追加计数，不新增消息（单测）

**前置条件**：循环干预策略为 `retry`，最后一个 user 消息无 retry_count。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env), assistant(循环内容)]`
2. 调用循环干预逻辑（retry 方式）

**预期**：
- `a.messages` **长度不变**
- 最后一条 user 消息 env 中出现 `<retry_count>1</retry_count>`
- user 指令文本不变，无 loop_feedback 标记

### UC-0005 retry 再次触发：计数+1，原提示词不动（单测）

**前置条件**：循环干预策略为 `retry`，最后一个 user 消息带 retry_count=1（无 loop_feedback 标记）。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env 含 retry_count=1), assistant(循环内容)]`
2. 再次调用循环干预逻辑（retry 方式）

**预期**：
- `a.messages` 长度不变
- env 中 `<retry_count>` 更新为 2
- user 指令文本不变

### UC-0006 retry 遇到 feedback 消息：计数+1，feedback 文本保留（单测）

**前置条件**：循环干预策略为 `retry`，最后一个 user 消息是 feedback 消息（带 loop_feedback 标记 + retry_count=1）。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env), assistant(循环内容), user(feedback 消息, retry_count=1)]`
2. 调用循环干预逻辑（retry 方式）

**预期**：
- `a.messages` 长度不变
- feedback 消息 `[0]` 文本保留不变
- env 中 `<retry_count>` 更新为 2
- `<loop_feedback>true</loop_feedback>` 保留

### UC-0007 temperature 方式与 retry 行为一致（单测）

**前置条件**：循环干预策略为 `temperature`，温度控制器已初始化。

**步骤**：
1. 构造消息序列：`[system, user(真实指令+env), assistant(循环内容)]`
2. 调用循环干预逻辑（temperature 方式，先增大温度）

**预期**：
- 温度被调整（`llmClient.SetTemperature` 被调用）
- 消息处理与 UC-0004 一致：最后 user 消息 env 追加减数 `retry_count=1`，不新增消息
- 无 loop_feedback 标记

### UC-0008 retry 遇到无 env 消息：先补完整 env 再附计数（单测）

**前置条件**：循环干预策略为 `retry`，最后一个 user 消息是纯文本（无 ContentParts、无 env）。

**步骤**：
1. 构造消息序列：`[system, user(纯文本无 env), assistant(循环内容)]`
2. 调用循环干预逻辑（retry 方式）

**预期**：
- 最后一条 user 消息被转换为 ContentParts 格式：`[0]`=原文，`[1]`=完整 env（含 time/cwd 等及 `<retry_count>1</retry_count>`）
- 原文文本保持不变

### UC-0009 feedback 消息 env 含完整环境上下文（单测）

**前置条件**：循环干预策略为 `prompt`。

**步骤**：
1. 构造含任务计划的消息序列
2. 触发 prompt 干预，检查生成的 feedback 消息 env 内容

**预期**：
- feedback 消息的 `<environment_details>` 包含：`<time>`、`<message_no>`、`<context_window>`、`<cwd>`、`<files>`、`<task_plan>`、`<opened_resources>` 全部块（与普通 user 消息一致）
- `<loop_feedback>` 与 `<retry_count>` 位于 `<environment_details>` 内部

### UC-0010 多轮循环链：prompt 计数持续递增直到链结束（单测，连环场景）

**前置条件**：循环干预策略为 `prompt`。

**步骤**：
1. 从空消息序列开始
2. 依次触发 3 次 prompt 循环干预（中间穿插 assistant 循环内容）
3. 触发一次新请求（追加新真实 user 消息）
4. 再次触发 prompt 循环干预

**预期**：
- 前 3 次干预：消息序列中只有 1 条 feedback 消息，retry_count 依次为 1、2、3
- 新请求追加真实 user 消息后：新 feedback 消息（retry_count=1）追加在真实 user 消息之后，旧 feedback 消息保留（各自计数独立）
- 每轮循环链内不产生多条 feedback 消息

### UC-0011 回归：sync 循环分支与 applyLoopIntervention 共用同一逻辑（单测）

**前置条件**：两处注入点（run_stream.go `loopDetectCrit` 分支、loop.go `applyLoopIntervention`）均改造为调用统一 helper。

**步骤**：
1. 分别从两个入口触发循环干预（同策略、同初始状态）
2. 比较两条路径产生的消息结构

**预期**：
- 两条路径最终消息结构完全一致（同一 helper 产生）
- 修复前：sync 路径产生的 feedback 消息无 env（纯文本 Content），applyLoopIntervention 路径同样无 env

### UC-0012 运行时验证：实际循环场景消息结构正确（运行时）

**前置条件**：
- 配置 `loop-juage-disabled`（或 loop-judge-enabled=off），`loop-intervention=prompt`，`show-loop-detection=on`
- 使用可稳定触发循环的测试指令（如反复让 LLM 输出相同内容）

**步骤**：
1. 启动 co-shell
2. 输入一个会触发循环检测的指令
3. 观察循环反馈发送提示，开启 llm-log 检查实际发送给 LLM 的 messages 数组

**预期**：
- 循环干预时追加的 feedback user 消息 ContentParts 为 2 段：提示词 + 含 `<loop_feedback>true</loop_feedback>` 和 `<retry_count>1</retry_count>` 的 env
- 再次循环时 retry_count 变为 2，且不新增 feedback 消息
- LLM 上下文中的其余 user 消息 env 不受影响

4. 上述 UC-0001 ~ UC-0012 全部通过（单测为主，UC-0012 可配合 llm-log 人工确认）。
5. 回归：`go test ./...` 全绿。
