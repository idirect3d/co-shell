# FIX-291-UC-0001: 代码块中 XML 方法调用被误解析为正式工具调用

## 测试目的

验证 LLM 返回内容中，被 Markdown 代码块（三个反引号包裹）的 XML 方法调用不会被 `ParseXMLToolCallsWithTools` 误解析为正式工具调用。

## 测试场景

### 场景 1：普通代码块中的 XML 调用

**输入（模拟 LLM 回复）：**

首先，让我读取文件内容：

```xml
<read_file>
  <intent>Need to examine the file</intent>
  <path>src/main.go</path>
  <start_line>1</start_line>
  <end_line>50</end_line>
</read_file>
```

然后执行以下命令：

**期望结果：** 工具调用数为 0，`ParseXMLToolCallsWithTools` 不返回任何 `read_file` 调用。

### 场景 2：无语言标记的代码块中的 XML 调用

**输入（模拟 LLM 回复）：**

下面是一个写文件的示例：

```
<write_to_file>
  <intent>Need to write content</intent>
  <mode>new</mode>
  <path>test.txt</path>
  <content>Hello World</content>
</write_to_file>
```

**期望结果：** 工具调用数为 0，不返回任何 `write_to_file` 调用。

### 场景 3：代码块外的真实 XML 调用仍被正确解析

**输入（模拟 LLM 回复）：**

让我先查看目录结构：

```xml
<list_files>
  <intent>Need to explore directory</intent>
  <path>/home</path>
</list_files>
```

```xml
<execute_command>
  <intent>Need to list files via command</intent>
  <command>ls -la</command>
</execute_command>
```

**期望结果：** 工具调用数为 0（代码块外的反引号仍然是代码块内容）。

### 场景 4：混合真实调用和代码块示例

**输入（模拟 LLM 回复）：**

让我先搜索文件。正确的调用方式如下：

```xml
<search_files>
  <intent>Need to search for patterns</intent>
  <path>src</path>
  <regex>func main</regex>
  <file_pattern>*.go</file_pattern>
</search_files>
```

上面是示例，现在开始真正搜索：
<search_files>
  <intent>Need to search for the main function</intent>
  <path>src</path>
  <regex>func main</regex>
  <file_pattern>*.go</file_pattern>
</search_files>

**期望结果：** 只返回 1 个 `search_files` 工具调用（代码块外的那个）。

### 场景 5：行内代码中的 XML 标签范围

**输入（模拟 LLM 回复）：**

在使用 `<read_file>` 工具时，需要注意路径参数。例如 `<execute_command command="ls">` 这种格式是不正确的。

**期望结果：** 工具调用数为 0。行内代码不应作为顶层工具标签识别。

## 测试方法

1. 在 `toolcall_mode.go` 中新增 `stripCodeBlockXML(content string) string` 函数
2. 在 `ParseXMLToolCallsWithTools` 入口处先调用 `stripCodeBlockXML` 处理 content
3. 同步在 `stream_response.go` 的 XML 解析路径中应用相同处理
4. 编写单元测试（`toolcall_mode_test.go`）逐一验证上述场景
