# FIX-518 测试用例 — 刷新后高 CPU / 输入卡顿（工作区刷新风暴）

> 分支：FIX-518
> 版本：v0.56.1
> 关联任务：FIX-518
> 关联特性：FEATURE-507（`history_get` 历史回放）、FEATURE-508（滑动窗口缓存）、FEATURE-444/375（`/api/tree` 文件树与 git 状态）

## 现象与根因（已实测确认）

**现象**：刷新 Web UI 后 10–20 秒内 CPU 占用极高，焦点落在主输入框时输入/聚焦极慢、卡顿，随后自行恢复。用户反馈该现象已存在数个版本。

**根因链（逐条均有证据）**：

| # | 环节 | 证据 |
|---|------|------|
| 1 | 刷新时前端请求并回放一页历史事件（`history_get` → `renderHistory()` 逐条 `renderEvent()`） | `app.js` FEATURE-507/508 实现 |
| 2 | `renderEvent()` 在 `token_iter`、`done`、工具调用结束三类事件上各调用一次 `refreshBranch()+loadTree()` | app.js:1556、1600、1891（改前行号） |
| 3 | `loadTree()` = `fetch("api/tree")` + 清空并重建整棵文件树 DOM，**无任何节流** | app.js `loadTree()` 实现 |
| 4 | `/api/tree` 每次递归遍历整个工作区（深度 ≤8、每目录 ≤500 项，跳过 `.git/node_modules/db/log/tmp`）并执行 git status | `web/server.go` `buildTree()` / `gitStatusMap()` |
| 5 | 本仓库工作区实测 **4065 目录 / 16753 文件**，`/api/tree` 单次响应 **6,567,740 B（6.3 MB）**，服务端 155 ms | `curl -w` 实测 + 响应解析 |
| 6 | 事件量：最大会话 **3279 条事件**，其中 `token_iter` 545、`tool_call` 1334 | 只读解析 `db/co-shell.db` 副本 |
| 7 | 结论：一页历史含数十条上述事件 → 几十~上百次「6.3 MB 树请求 + JSON 解析 + 整树 DOM 重建」 | 1+2+3+5+6 |

**修复**（`web/static/app.js`）：

1. 新增 `scheduleWorkspaceRefresh(immediate)`：合并工作区刷新请求。
   - `historyReplaying` 为真时：仅置 `workspaceRefreshPending`，不发起请求；
   - 其余情况：300 ms 去抖（`WORKSPACE_REFRESH_DEBOUNCE_MS`）后执行一次；
   - `immediate`：跳过去抖，立即执行。
2. 三类高频事件改为调用 `scheduleWorkspaceRefresh()`（不再直接 `refreshBranch()+loadTree()`）。
3. `renderHistory()` 全程持有 `historyReplaying`，`endHistoryReplay()` 释放，并仅在有待处理请求时刷新一次。
4. 用户主动动作（上传、`revealInTree`、session 截断、首屏加载）仍直接刷新。

## 验收标准

- 刷新页面后，回放期间**不再发起** `/api/tree` 请求；整段回放结束后最多发起 **1 次**。
- 刷新后主线程不再被长时间占满：输入框可立即聚焦与输入，无 10–20 秒卡顿。
- 运行时（非回放）：连续的 `token_iter` / 工具调用只触发合并后的刷新（300 ms 窗口内多次请求合并为一次）。
- 功能不回归：文件树在迭代/工具调用结束后仍会更新（最多延迟 300 ms）；git 分支标签仍会刷新；用户主动操作（上传文件、在树中定位文件）后树立即更新。
- `go build ./... && go vet ./...` 通过；`node --check web/static/app.js` 通过。

## 运行时用例

### UC-0001 刷新后回放期间不发起 /api/tree 请求（核心）

**前置条件**
- 工作区含大量文件（本仓库：约 1.7 万个文件），`/api/tree` 响应约 6.3 MB。
- 会话历史中至少有 20 个消息组、且含 `token_iter` 与 `tool_call` 事件。

**步骤**
1. 在页面注入 `fetch` 计数器（包裹 `window.fetch`，统计 `api/tree` 调用次数与发生时刻）。
2. 刷新页面。
3. 观察从 WebSocket 收到 `history` 消息到回放结束（`endHistoryReplay` 触发）这段时间内的 `api/tree` 调用次数。

**预期**
- 回放期间 `api/tree` 调用次数为 **0**。
- 回放的最后一条事件渲染完成后，才出现至多 1 次 `api/tree` 调用。
- 网络面板中不再出现数十次的 6.3 MB 请求。

### UC-0002 回放结束后只刷新一次（数量断言，核心）

**步骤**
1. 同上注入计数器，并记录刷新后 5 秒内的 `api/tree` 与 `api/bootstrap` 调用次数。
2. 刷新页面，等待 5 秒。

**预期**
- `api/tree` 总次数 ≤ 2（首屏 1 次 + 回放结束 1 次；若首屏与回放合并则可能为 1 次）。
- 改前同场景下该数字为**数十次**（与历史中 `token_iter` / `tool_call` 数量同阶）。
- 页面总传输字节量下降 1–2 个数量级。

### UC-0003 刷新后输入框可立即响应（无长时卡顿，核心）

**步骤**
1. 刷新页面。
2. 在页面加载后 1 秒内点击主输入框并连续输入一段文本（或运行连续按键脚本）。
3. 观察输入回显延迟与 `PerformanceObserver` 记录的 longtask 总时长。

**预期**
- 输入字符即时回显，无明显延迟或丢字。
- 加载后 5 秒内 longtask 总时长显著低于改前（改前主线程被数十次 6.3 MB 解析 + DOM 重建占满十余秒）。
- 无「焦点放入输入框后动作极慢」的现象。

### UC-0004 运行时连续事件合并为一次刷新（去抖）

**步骤**
1. 正常触发一轮 agent 运行（产生多个 `token_iter` 与若干工具调用）。
2. 统计 `api/tree` 的请求时刻。

**预期**
- 同一 300 ms 窗口内的多次 `scheduleWorkspaceRefresh()` 调用只产生 **1 次** `api/tree` 请求。
- 各次请求之间的间隔不小于去抖窗口（除 `immediate` 调用外）。

### UC-0005 迭代/工具调用结束后文件树仍会更新（不回归）

**步骤**
1. 让 agent 新建一个文件（或工作区内手动新增文件，再触发一次工具调用/迭代结束）。
2. 观察左侧文件树。

**预期**
- 文件树在事件结束后 **≤300 ms** 内自动更新，新增文件可见。
- 不需要手动刷新页面。
- 树的展开状态保持（`expandedDirs` 行为不变）。

### UC-0006 用户主动操作（上传 / 树中定位）立即刷新（不回归）

**步骤**
1. 通过输入框上传一个附件。
2. 在文件预览中点击路径以在树中定位（`revealInTree`）。

**预期**
- 上传完成后文件树立即出现新文件（未经去抖延迟）。
- 定位操作会展开祖先目录并高亮目标文件，行为与改前一致。

### UC-0007 首页加载仍会加载一次文件树（不回归）

**步骤**
1. 清空缓存并打开页面（无历史回放或历史为空）。
2. 观察文件树与 `api/tree` 调用。

**预期**
- 页面加载时仍发起 1 次 `api/tree`，文件树正常渲染。
- 该调用不被去抖延迟（首屏直接调用 `loadTree()`，保持原行为）。

### UC-0008 回放期间的分支标签也一并延迟刷新（边界）

**步骤**
1. 在回放期间观察侧边栏「工作区 · <分支>」标签是否发生多次更新。
2. 回放结束后观察该标签。

**预期**
- 回放期间 `api/bootstrap` 调用为 0。
- 回放结束后 `refreshBranch()` 执行一次，分支名与当前分支一致。

### UC-0009 分页加载（向上滚动追加更早一页）同样受抑制（边界）

**步骤**
1. 在消息区滚动到最顶端，触发 `loadOlderHistory`（`before` 游标分页）。
2. 统计该页回放期间的 `api/tree` 调用。

**预期**
- 该页回放期间同样为 0 次 `api/tree`；结束后至多 1 次。
- 视口锚定行为不变（追加的历史页插入在顶部，当前阅读位置不跳动）。

### UC-0010 无待处理请求时回放结束不产生多余刷新（边界）

**步骤**
1. 构造一页历史事件，其中不含 `token_iter` / `done` / 工具调用结束事件（例如仅 `content` 事件）。
2. 刷新并观察。

**预期**
- 回放结束后**不**产生额外的 `api/tree` 请求（`workspaceRefreshPending` 为假时不刷新）。
- 页面仍正常渲染历史内容。

## 验证方式说明

- 运行时用例以**请求计数 + 时间线采样**为主：在页面内包裹 `window.fetch` 记录每个 `api/tree` / `api/bootstrap` 的调用时刻与耗时，回放前后分别采样，即可断言 UC-0001/0002/0004/0008/0009/0010。
- UC-0003 用 `PerformanceObserver({entryTypes:['longtask']})` 累计长任务时长与输入回显延迟量化。
- 验证在**独立实例**上进行，避免影响用户正在使用的实例（历史回放需要真实历史，独立实例可先用脚本灌入事件或复用历史文件）。
