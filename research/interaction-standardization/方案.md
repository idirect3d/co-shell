# 工具调用交互标准化方案

> 版本：v0.1（讨论稿）
> 日期：2026-08-21
> 状态：待讨论

## 1. 背景与问题

co-shell 的 Agent 在执行工具调用时，存在三类需要用户参与的交互：

1. **意图字段（intent）**：每个工具调用都带一个 `intent` 参数，说明"为什么调用这个工具"。目前通过 `buildToolSummary`（调用前摘要）和 `buildToolOutcome`（调用后回执）以**文本**形式展示。
2. **用户选择/输入参数**：`ask_followup_question` 工具让 LLM 向用户提问，用户可选项或自由输入。
3. **确认放行（confirm-tool）**：工具执行前需用户确认，支持 Enter(批准)、c(取消)、a(全部批准)、g(禁用确认)、d(永久禁用)、N(批准N次)、其他(补充指令)。

### 1.1 现状问题

这三类交互目前都是通过 `UserIO` 的**底层原语**（`Print*` + `ReadLine/ReadKey`）拼装出来的，交互逻辑散落在各工具回调里：

| 交互 | 实现位置 | 输出方式 | 输入方式 |
|------|---------|---------|---------|
| 意图摘要 | `tool_summary.go` | `EventToolCall` 事件（文本） | — |
| 提问/选择 | `tools.go: askFollowupQuestionTool` | `io.Println/Printf` | `io.ReadLine` |
| 确认放行 | `command_tools.go: promptToolConfirmation` | `io.Println/Printf` | `io.ReadLine` |

**由此导致的问题：**

1. **交互逻辑与渲染耦合**：确认放行的键位（Enter/c/a/g/d/N）、提问的选项编号，都硬编码在工具回调里，TUI 和 Web UI 无法结构化感知。
2. **Web UI 体验割裂**：Web UI 只能看到 `ui_text` 文本 + 通用 `ask` 输入框。确认放行在 Web 上表现为"一段文本 + 一个输入框"，用户必须手动输入 `a`/`g`/`N` 等，无法获得按钮式确认、放行次数选择等原生体验。
3. **前端硬编码键位**：`app.js` 的 `showAsk` 硬编码了 `[["Enter",""],["c","c"],["a","a"],["g","g"],["d","d"],["n","n"]]`，与后端 `promptToolConfirmation` 的键位逻辑耦合，一旦后端调整键位前端必须同步改。
4. **无法区分交互类型**：Web 端无法区分"普通输入"、"选项选择"、"确认放行"、"放行次数输入"等不同交互，无法针对性地渲染。
5. **意图展示不统一**：`buildToolSummary` 用 i18n 模板逐工具定制，`ToolCallRenderer` 用流式 diff 渲染，两套逻辑并存，展示形式不统一。

### 1.2 目标

引入一个**统一的交互模型**，把"交互"从底层原语拼装提升为**结构化声明**，使 TUI 和 Web UI 能基于同一份结构化数据，各自渲染出统一、规整的体验。

- **统一交互类型**：确认放行、选项选择、自由输入、放行次数输入等，都有标准化的类型标识。
- **统一数据结构**：每个交互请求携带结构化字段（标题、正文、选项、键位、默认值等），响应携带结构化结果。
- **统一输出协议**：TUI 和 Web UI 消费同一份结构化事件，各自渲染。
- **意图字段标准化**：intent 的展示统一为结构化字段，而非散落的 i18n 模板。

## 2. 统一交互模型（Interaction）

### 2.1 核心概念

引入 `Interaction` 结构体，作为所有用户交互的**单一数据载体**。工具回调不再直接调用 `io.Println/ReadLine`，而是构造一个 `Interaction` 交给统一的 `InteractionManager` 处理。

```
┌─────────────────────────────────────────────────────────┐
│                    工具回调 (Tool Callback)               │
│                                                         │
│  构造 Interaction 对象 → 交给 InteractionManager        │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│              InteractionManager (统一交互管理器)          │
│                                                         │
│  1. 通过 UserIO 渲染请求（TUI: 文本+按键 / Web: 结构化）  │
│  2. 通过 UserIO 读取响应（TUI: ReadLine / Web: ask）     │
│  3. 解析响应为结构化结果，返回给工具回调                  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 Interaction 数据结构

```go
// InteractionKind 标识交互类型
type InteractionKind string

const (
    InteractionConfirm  InteractionKind = "confirm"  // 确认放行（含放行次数）
    InteractionSelect   InteractionKind = "select"   // 选项选择（ask_followup_question 带 options）
    InteractionInput    InteractionKind = "input"    // 自由输入（ask_followup_question 无 options）
    InteractionKey      InteractionKind = "key"      // 单键确认（通用）
)

// Interaction 是一次用户交互的完整声明
type Interaction struct {
    Kind    InteractionKind // 交互类型
    Title   string          // 标题（如工具摘要、问题）
    Body    string          // 正文（风险提示、补充说明）
    Options []string        // 选项列表（select 用）
    Keys    []KeyOption     // 键位选项（confirm/key 用）
    Default string          // 默认值（Enter 对应的值）
    AllowFree bool          // 是否允许自由输入（confirm 的补充指令 / input）
}

// KeyOption 是一个键位选项
type KeyOption struct {
    Label string // 显示标签（如 "批准"、"取消"）
    Key   string // 触发键（如 ""=Enter, "c", "a", "g", "d"）
    Value string // 返回给后端的值
    Hint  string // 悬停提示（Web 用）
}

// InteractionResult 是用户交互的结构化结果
type InteractionResult struct {
    Action  string // 动作标识（如 "approve"、"cancel"、"approve_all"、"approve_count"、"modify"、"select"、"input"）
    Value   string // 值（如放行次数 N、选中的选项、自由输入内容）
    Raw     string // 原始输入（保留）
}
```

### 2.3 InteractionManager 接口

```go
// InteractionManager 统一处理用户交互
type InteractionManager interface {
    // Ask 发起一次交互，返回结构化结果
    Ask(ctx context.Context, in Interaction) (InteractionResult, error)
}
```

**TUI 实现（TerminalInteractionManager）**：
- 用 `io.Println/Printf` 渲染标题、正文、选项、键位提示
- 用 `io.ReadLine` 读取输入
- 解析输入为 `InteractionResult`

**Web 实现（WebInteractionManager）**：
- 通过 WebSocket 推送结构化 `interaction` 消息（含完整 Interaction 数据）
- 前端渲染为按钮组/选项列表/输入框
- 用户操作后回传结构化 `InteractionResult`

## 3. 输出协议

### 3.1 事件流扩展

在现有 `StreamEvent` 基础上，新增一个交互事件类型，携带完整的 `Interaction` 数据：

```go
const EventInteraction = "interaction" // 用户交互请求

// StreamEvent.Meta 新增键
const (
    MetaKeyInteraction = "interaction" // Interaction 的 JSON 序列化
    MetaKeyInteractionID = "interaction_id" // 交互唯一 ID（用于 Web 回传）
)
```

**TUI 渲染**：`LineRenderer` 识别 `EventInteraction`，用文本形式渲染（标题 + 选项 + 键位提示），然后通过 `UserIO.ReadLine` 读取。

**Web 渲染**：`WebRenderer` 识别 `EventInteraction`，把 `Meta[MetaKeyInteraction]` 解析为结构化数据，前端渲染为交互组件。

### 3.2 WebSocket 协议

**下行（server → browser）**：
```json
{
  "kind": "interaction",
  "id": "interaction-1",
  "interaction": {
    "kind": "confirm",
    "title": "⚙️ execute_command: ls -la",
    "body": "⚠️ 此操作可能影响系统，请确认。",
    "keys": [
      {"label": "批准", "key": "", "value": "approve"},
      {"label": "取消", "key": "c", "value": "cancel"},
      {"label": "全部批准", "key": "a", "value": "approve_all"},
      {"label": "禁用确认", "key": "g", "value": "approve_g"},
      {"label": "永久禁用", "key": "d", "value": "approve_d"},
      {"label": "批准N次", "key": "n", "value": "approve_count"}
    ],
    "allow_free": true
  }
}
```

**上行（browser → server）**：
```json
{
  "type": "interaction_answer",
  "id": "interaction-1",
  "result": {
    "action": "approve_count",
    "value": "3"
  }
}
```

### 3.3 前端渲染

前端根据 `interaction.kind` 渲染不同组件：

| kind | 渲染组件 |
|------|---------|
| `confirm` | 按钮组（批准/取消/全部批准/禁用确认/永久禁用/批准N次）+ 自由输入框 |
| `select` | 选项列表（单选按钮）+ 取消选项 |
| `input` | 自由输入框 |
| `key` | 单键按钮组 |

这样前端不再硬编码键位，而是从 `interaction.keys` 动态渲染。

## 4. 意图字段标准化

### 4.1 现状

`buildToolSummary` 用 i18n 模板逐工具定制（`KeyToolCallSummaryExecCmd` 等），`ToolCallRenderer` 用流式 diff 渲染。两套逻辑并存。

### 4.2 方案

将工具摘要统一为**结构化字段**，而非散落的 i18n 模板：

```go
// ToolSummary 是工具调用的结构化摘要
type ToolSummary struct {
    ToolName string            // 工具名
    Intent   string            // 意图
    Params   []SummaryParam    // 关键参数
}

type SummaryParam struct {
    Name  string // 参数名
    Value string // 参数值（已截断/脱敏）
    Kind  string // "path" | "count" | "text" | ...
}
```

`buildToolSummary` 改为返回 `ToolSummary` 结构体，`EventToolCall` 事件的 `Meta` 携带其 JSON。TUI 和 Web UI 各自渲染：
- **TUI**：`⚙️ execute_command: ls -la (列出文件)` 文本形式
- **Web**：结构化卡片（工具名 + 意图 + 参数列表）

这样意图展示统一为结构化数据，i18n 模板只负责"字段标签"的翻译，不再负责整句拼装。

## 5. 改造范围

### 5.1 需要改造的交互点

| 交互点 | 现状 | 改造后 |
|--------|------|--------|
| `promptToolConfirmation` | 直接 `io.Println/ReadLine` | 构造 `Interaction{Kind: confirm}` 交给 `InteractionManager` |
| `askFollowupQuestionTool` | 直接 `io.Println/ReadLine` | 构造 `Interaction{Kind: select/input}` 交给 `InteractionManager` |
| `buildToolSummary` | 返回字符串 | 返回 `ToolSummary` 结构体 |
| `buildToolOutcome` | 返回字符串 | 返回 `ToolOutcome` 结构体（可选） |
| `WebIO` | `Print*`→ui_text, `ReadLine`→ask | 新增 `InteractionManager` 实现，推送结构化 interaction |
| `app.js showAsk` | 硬编码键位 | 从 interaction.keys 动态渲染 |

### 5.2 兼容性

- **TUI 保持现状**：`TerminalInteractionManager` 用现有 `UserIO` 原语渲染，输出形式与现在基本一致（甚至更规整）。
- **Web 增强**：`WebInteractionManager` 推送结构化数据，前端渲染为原生交互组件。
- **向后兼容**：`UserIO` 接口不变，`InteractionManager` 是新增抽象，工具回调逐步迁移。

## 8. 交互示例对比

### 8.1 确认放行（confirm-tool）

**标准化前（TUI）**：
```
⚙️ execute_command: ls -la (列出文件)
⚠️ 此操作可能影响系统，请确认。

确认执行? [Enter=批准, c=取消, a=全部批准, g=禁用确认, d=永久禁用, N=批准N次, 其他=补充指令]:
```

**标准化前（Web）**：
```
[ui_text] ⚙️ execute_command: ls -la (列出文件)
[ui_text] ⚠️ 此操作可能影响系统，请确认。
[ask line] 确认执行? [Enter=批准, c=取消, ...]:
[输入框] 用户必须手动输入 a/g/N 等

[Enter] 批准   [c] 取消   [a] 全部批准   [g] 禁用确认   [d] 永久禁用   [N] 批准N次

**标准化后（Web）**：前端根据 `interaction.keys` 动态渲染按钮组：
```
┌─────────────────────────────────────────────┐
│ ⚙️ execute_command: ls -la (列出文件)        │
│ ⚠️ 此操作可能影响系统，请确认。               │
│                                             │
│ [批准] [取消] [全部批准] [禁用确认] [永久禁用] │

## 9. 风险与权衡

1. **改造范围较大**：涉及 `promptToolConfirmation`、`askFollowupQuestionTool`、`buildToolSummary` 等多个核心函数，需分阶段实施，每阶段验证 TUI 行为不变。
2. **Web 协议变更**：新增 `interaction` 消息类型，需同步更新前端 `app.js` 和 WebSocket 协议文档。
3. **兼容性**：`UserIO` 接口不变，`InteractionManager` 是新增抽象，现有 TUI 行为通过 `TerminalInteractionManager` 保持。
4. **测试覆盖**：需为 TUI/Web 双端补充单元测试，确保交互逻辑一致。

## 10. 验收标准

1. TUI 下确认放行、提问/选择、意图摘要的展示形式与现在一致或更规整。
2. Web 下确认放行渲染为按钮组，提问/选择渲染为选项列表，意图摘要渲染为结构化卡片。
3. 前端不再硬编码确认键位，从 `interaction.keys` 动态渲染。
4. 所有交互点通过 `InteractionManager` 统一处理，工具回调不再直接调用 `io.Println/ReadLine`。
5. `go build/vet/test ./...` 全绿。

## 11. 决策记录（讨论确认）

> 本节记录方案讨论中已确认的决策，作为后续开发的依据。

### 11.1 InteractionManager 采用独立接口（方案 B）

**决策**：新建独立接口 `InteractionManager`，而非扩展 `UserIO`。

**理由**：
- 职责清晰：`UserIO` 管"怎么读写"（底层原语），`InteractionManager` 管"交互是什么"（高层语义）
- 交互逻辑（键位/选项解析）只写一次，通过**组合**复用 `UserIO` 的底层能力
- 对现有 `StdioIO`/`EnhancedIO`/`WebIO` 零侵入，改动最小
- 未来扩展交互类型不影响底层 I/O

**实现要点**：
- `TerminalInteractionManager` 内部持有 `UserIO`，用其 `Print*`/`ReadLine` 渲染和读取，键位/选项解析逻辑在 manager 层共享
- `WebInteractionManager` 内部持有 `WebIO`，用其 `ask` 机制推送结构化交互

### 11.2 确认放行键位保持固定（不支持用户自定义）

**决策**：确认放行的键位（Enter/c/a/g/d/N）保持固定，不支持用户自定义。

**理由**：
- 键位是低频操作，自定义价值有限
- 增加配置项、冲突校验、前端同步等复杂度，与"简洁优先"原则冲突
- 键位已数据化（`Interaction.Keys`），未来如需自定义只需改数据来源，扩展成本低

**改进方向**：不同交互场景使用不同的键位集（场景内固定、场景间不同）：
- 确认放行：`Enter/c/a/g/d/N`
- 提问选择：`1/2/3...` + 取消
- 单键确认：`Enter/c`

### 11.3 ToolSummary 覆盖所有工具

**决策**：`ToolSummary` 结构化摘要覆盖**所有**工具，而非只覆盖高频工具。

**实现要点**：
- 每个工具定义其关键参数（`SummaryParam`），包括参数名、值、类型
- 高频工具（execute_command/read_file/write_to_file 等）有定制化的参数展示
- 低频工具使用通用 fallback（工具名 + 意图 + 全部参数）
- i18n 模板只负责"字段标签"翻译，不再负责整句拼装

### 11.4 Web 端"批准N次"提供预设按钮

**决策**：Web 端"批准N次"提供预设按钮 **3 / 10 / 50**，同时保留自由输入。

**实现要点**：
- `Interaction.Keys` 中 `approve_count` 键位携带预设值 `[3, 10, 50]`
- 前端渲染为三个预设按钮 + 一个数字输入框
- 用户点击预设按钮直接回传对应次数，或在输入框输入自定义次数
