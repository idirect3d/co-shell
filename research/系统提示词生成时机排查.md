# 系统提示词生成时机排查报告

> 目标：确认系统提示词的生成时机，评估「只在新建会话时生成一次、之后持久化不变」以最大化前缀缓存（prefix cache）的可行性。
>
> 排查日期：2026-09-11　版本：v0.48.0 [BUILD-941]

---

## 一、结论速览

| 问题 | 结论 |
|------|------|
| 系统提示词存在哪里？ | `Agent.systemPrompt` 字段 + `a.messages[0]`（role=system） |
| 是否每次 LLM 请求都重新生成？ | **否**。每次 LLM 请求只是把 `a.messages[0]` 原样带上，不重新构建 |
| 是否每次用户输入都重新生成？ | **是**。`RunStream` / `Run` 入口各调用一次 `rebuildSystemPrompt()` |
| 是否每次迭代都重新生成？ | **否**（循环体内无调用），但注释暗示曾有此行为 |
| 内容是否会变化？ | **基本不会**。`{TASK}`/`{TASK_PLAN}` **不在系统提示词中**（见 §4.1 更正） |
| 改造可行性 | **可行且风险低** —— 系统提示词本身已接近静态 |

## 二、生成入口与缓存字段

纯函数，无副作用；按 `getWorkModeSectionNames()` 顺序拼接各 section，用 `KeySectionSeparator` 分隔。

### 2.2 缓存字段

`agent/loop.go:79`

```go
systemPrompt     string   // 缓存最近一次构建结果
```

`agent/agent.go:1219-1228`（`rebuildSystemPrompt` 尾部）

```go
a.systemPrompt = buildSystemPromptWithMode(...)
a.mu.Lock()
defer a.mu.Unlock()
if len(a.messages) > 0 {
    a.messages[0] = llm.Message{Role: "system", Content: a.systemPrompt}
} else {
    a.messages = []llm.Message{{Role: "system", Content: a.systemPrompt}}
}
```

**关键点**：构建结果同时写入 `a.systemPrompt` 与 `a.messages[0]`，二者保持一致。

### 2.3 每次 LLM 请求的行为

`agent/stream_response.go:113`

```go
eventCh, err := a.llmClient.ChatStream(streamCtx, contextMsgs, tools)
```

`contextMsgs` 由 `loop.go:487-521` 组装，**直接取 `a.messages[0]` 作为 system 消息**，不重新构建：

```go
systemMsg := a.messages[0]
historyMsgs := a.messages[startIdx:]
msgs = append(msgs, systemMsg)
msgs = append(msgs, historyMsgs...)
```

✅ **结论**：单次 LLM 请求内不会重新生成系统提示词。

## 四、内容变化因素分析

### 4.1 动态占位符 —— 更正：`{TASK}`/`{TASK_PLAN}` 不在系统提示词中 ⚠️

**实测验证**（用独特标记渲染系统提示词）：

```
=== 系统提示词长度: 12037
=== 含 UNIQUE_TASK_MARKER_XYZ ? false
=== 含 UNIQUE_PLAN_MARKER_ABC ? false
=== 含字面 {TASK} ? false
=== 含字面 {TASK_PLAN} ? false
```

**结论**：

1. `buildSystemPromptWithMode` 虽接收 `taskDesc` / `taskPlanText` 两个参数，但**函数体内从未使用 `taskPlanText`**；`taskDesc` 仅赋给 `env.taskDesc`，而**没有任何 section 文本包含 `{TASK}` 占位符**，因此替换是空操作。
2. `{TASK}` / `{TASK_PLAN}` 实际只出现在 **loop judge / problem solver 的 user prompt**（`i18n/zh_loop.go:84,121`）与 **工具结果模板**（`KeyToolResultWithPlan`），**不在系统提示词中**。
3. 任务上下文实际通过 **`<environment_details>` 的 `<task_plan>` 块**注入到 **user 消息**（`agent/envelope.go:209-213`），而非系统提示词。

**因此：系统提示词本身不含随任务进展变化的内容。**

> 附带发现（死代码）：`buildSystemPromptWithMode` 的 `taskPlanText` 参数、`env.taskDesc` 字段、`{TASK}` 替换语句（`system_prompt.go:496`）均为无效代码，可考虑清理。

### 4.2 环境信息（基本稳定）

`env.cwd` / `env.shell` / `env.os` / `env.arch` / `env.execName` / `env.homeDir` / `env.lang` —— 进程生命周期内不变。

### 4.3 配置派生（变更时才变）

`agentName` / `agentDescription` / `agentPrinciples` / `userName` / `channel` / `contextReorganizeThreshold` / `resultModeInstruction` / `toolUsageText`。

### 4.4 磁盘内容（每次重建都重读）

`rebuildSystemPrompt` 每次都会：

- `config.LoadFromFile(cfgPath)` 重读 config.json（`agent.go:1166`）
- `a.resolveRules()` → `loadRulesDir()` 重读 `.rules/` 目录
- `loadSectionText()` 重读 `mode/*.md`

⚠️ 这意味着**即使内容没变，每次也做一遍磁盘 I/O**；且若 `.rules/` 或 `mode/*.md` 被外部修改，提示词会静默变化。

### 4.5 无时间戳

✅ 系统提示词**不含** `time.Now()`。`{CURRENT_TIME}` 只出现在**工具结果消息**（`agent.go:1553,1596`），不在 system prompt 中。

## 五、前缀缓存影响评估

### 5.1 当前行为对缓存的影响

```
用户输入 1 → rebuildSystemPrompt() → system prompt A → 请求 1（缓存写入 A）
  迭代 2  → （不重建）           → system prompt A → 请求 2（缓存命中 A）✅
  迭代 3  → （不重建）           → system prompt A → 请求 3（缓存命中 A）✅
用户输入 2 → rebuildSystemPrompt() → system prompt B → 请求 4（缓存 miss，需重建）❌
```

**结论**：单次任务内的多轮迭代**能**命中缓存；每次新的用户输入会**重新构建**，但由于系统提示词内容**不含动态任务信息**，重建结果与上次**通常完全一致** —— 因此**前缀缓存实际仍然有效**（内容相同 → 前缀相同）。

### 5.2 真正的失效风险

系统提示词内容变化的**唯一来源**是：

1. **配置变更**（`SetConfig` / 模式切换 / `:set`）—— 低频、用户主动
2. **磁盘文件变更**（`.rules/*.md`、`mode/*.md`、`PRINCIPLES.md`）—— 低频、用户主动
3. **环境变化**（cwd / home / lang）—— 进程内基本不变

⚠️ 但存在一个**隐性风险**：`rebuildSystemPrompt` 每次都重读磁盘。若 `.rules/` 或 `mode/*.md` 被外部工具修改，系统提示词会**静默变化**，导致缓存失效且难以察觉。

## 六、改造建议

### 方案 A：清理死代码（推荐，零风险）

**思路**：`{TASK}`/`{TASK_PLAN}` 本就不在系统提示词中，相关参数与替换语句是死代码。清理后可消除误解。

- 清理项：`buildSystemPromptWithMode` 的 `taskPlanText` 参数、`env.taskDesc` 字段、`system_prompt.go:496` 的 `{TASK}` 替换
- 优点：零行为变化，代码更清晰
- 风险：低（需同步调整调用方签名）

### 方案 B：仅在新建会话时生成，之后冻结（推荐，达成用户目标）

**思路**：`RunStream`/`Run` 入口不再无条件重建，改为「仅当 `a.messages` 为空或会话切换时」重建。

- 优点：改动小，直接达成用户目标；由于系统提示词本就不含动态任务信息，**冻结不会丢失任何任务上下文**（任务上下文走 `<environment_details>` 的 user 消息）
- 缺点：`.rules/`、`mode/*.md`、`PRINCIPLES.md` 的外部修改不再自动生效（需显式 `RebuildSystemPrompt`）
- 风险：低-中（需确认热更新语义可接受）

### 方案 C：内容哈希去重（可与 B 叠加）

**思路**：`rebuildSystemPrompt` 构建后与 `a.systemPrompt` 比较，**内容相同则不写回** `a.messages[0]`。

- 优点：改动极小、零行为变化；避免「内容未变却重写消息」
- 缺点：不减少磁盘 I/O（构建本身仍执行）
- 风险：低

### 方案 D：B + C 组合（最优）

先做 C（去重，零风险），再做 B（仅在新建会话重建）。

## 七、待确认问题

1. **「新建会话」的准确定义**：当前会话切换**不重建**系统提示词（复用内存中的）。是否需要改为「切换/新建会话时重建一次」？
2. **`.rules/` 与 `mode/*.md` 的热更新**：当前每次重建都重读磁盘。若改为「只在新建会话生成」，这些文件的外部修改将不再自动生效（需显式 `RebuildSystemPrompt`）。是否可接受？
3. **死代码是否清理**：`buildSystemPromptWithMode` 的 `taskPlanText` 参数、`env.taskDesc`、`{TASK}` 替换语句均为无效代码，是否一并清理？
