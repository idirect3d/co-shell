# Token 优化基线方案与基线数据

- 日期：2026-10-01
- 对应设计：`research/token优化设计方案.md`
- 状态：**基线已采集（优化前），待开发后做同口径对比**

---

## 1. 目的

量化"多轮工具迭代时，每轮注入的 `<environment_details>` 带来的固定上下文开销及其累积增长"，作为优化前后对比的基准。

## 2. 方法

由于真实 LLM 会话受模型随机性影响（轮数、工具选择不可控），基线采用**确定性测量**：直接调用产品代码的 env 生成函数 `buildFullEnvironmentDetails()`，在与产品一致的运行目录（workspace 根）下生成真实信封，并按每轮一条 env 消息的方式累加，得到 12 轮迭代的上下文增长曲线。

- 测量工具：`agent/env_baseline_test.go`（`TestEnvBaselineGrowth`）
- 复现命令：
  ```bash
  go test ./agent -run TestEnvBaselineGrowth -v -count=1
  ```
- 标尺定义（与设计方案 A 方案的 L0/L1/L2 一致）：
  - **L0 完整**：现状全量信封（`buildFullEnvironmentDetails` 原始输出）
  - **L1 精简**：time / message_no / context_window / cwd / current_mode / no_tool_action / session_title / task_plan / opened_resources / sub_agents / board_replies
  - **L2 极简**：time + message_no

## 3. 基线数据

| ├ current_dir | 2,351 B | 45.9% |
| ├ tools（bin/） | 1,623 B | 31.7% |
| ├ research | 739 B | 14.4% |

### 3.3 工具声明（D 方案的量化依据）

- 运行时工具总数：**62 个**（`grep -c 'Callback: ' agent/tools.go`）
- 工具 schema 中重复的 `meta` 参数说明：
  - 出现次数 **72 次**，合计 **18,636 B**（≈4.7K tokens）
  - 即每轮请求中约 18.6KB 是**逐字重复**的同一段说明（`Transparency metadata object carrying intent/risk/...`），D1 的"meta 描述压缩"可直接回收这部分。
- 工具 schema 总体积的精确测量待补：当前基线测试中 `buildTools()` 在合成 Agent 上因缺少运行时依赖（MCP/Browser 管理器）触发 nil 解引用而被跳过；开发阶段应改为在真实 Agent 上测量（或用 `ToolDeclarations()` 后 JSON 序列化）。

## 5. 开发后的对比口径

优化实现后，用**完全相同的命令**再跑 3 次，逐项对比：

1. `cum_current` 曲线斜率应从 **+5,118 B/轮** 降到 **+114 B/轮** 量级（A+B 生效）；
2. `L0(full)` 体积应从 5,118 B 降到 **≤3,000 B**（C 生效；含 board_agents 时收益更大）；
3. 工具 schema 中 `meta` 重复说明应从 18,636 B 降到 **≤4,000 B**（D1 生效）；
4. 真实会话补充验证：跑一个 10 轮以上的真实任务（至少 3 次），记录每轮 `context_window`（`<environment_details>` 内的 token 行），确认上下文增长显著放缓、`reorganize_context` 触发轮次后移。

## 6. 已知局限

1. 合成 Agent 未启用 board / task plan / runtime_info，故 5,118 B 是**保守下限**，真实生产 L0 更大（优化收益也更大）；
2. 未覆盖系统提示词与工具 schema 的实际请求体积（属固定部分，D 方案的目标）；
3. 未做真实 LLM 端到端 token 采样（依赖 CLI 非交互模式，待开发阶段补）；
4. 测量以"字节"为单位，token 换算参考 3.7–4.0 字节/token（英文为主）。
