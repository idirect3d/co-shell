> 数据来源：`notes/tool_call_errors.md`（用户记录）、`log/tool-call-error-*.log`、`log/co-shell-2026-10-01.log`、本会话实时复现

## 1. 结论摘要

1. **报错主体不是"模型乱写参数"，而是 `meta.progress` 的规则在"系统提示词"与"后端校验"之间自相矛盾。**
   提示词写"只报告状态有变化的步骤以及当前正在执行的步骤，未变化的步骤可以不传"，
   代码（FEATURE-452）却要求"所有此前处于 `in_progress` 的步骤都必须出现在本次 progress 中"。
   模型按提示词只报"当前步骤"，后端判定"遗漏步骤"→ 整次工具调用被拒绝。

2. **"会话最开始报错更多"有三个叠加机制**（详见 §5）：
   入场时任务计划刚建立、常有多步/刚从 step N 推进到 N+1（最易触发上述矛盾）；
   计划尚未建立时"无内容可报"却仍被强制要求非空 progress；
   历史上下文中还没有任何"正确 meta 样例"可模仿。

3. **一个放大器：错误提示模板与真实错误不匹配。**
   `agent/tool_error.go` 把所有含 "missing/required/omit" 的错误都归为"缺少工具参数"，并回填该工具自身参数清单（如 read_file 的 `path`）——**从不提 meta**。
   于是一个 `meta.progress` 问题被回述为"你缺 path 参数"，模型无法据此修正，浪费重试甚至进入循环。

4. 其余为次要类别：`replace_in_file` 的 SEARCH 块不匹配（内容定位类）、模型端点 502（基础设施类），与 meta 机制无关。

## 4. 根因分析

### R1（主因 · 对应 A1"遗漏步骤"）提示词与校验规则互相矛盾

系统提示词同一条目（`i18n/zh_system.go:117`，英文版同段）里同时存在两句**互相冲突**的表述：

- 前半句：`其作用是精准调整变动的部分——只报告状态有变化的步骤以及当前正在执行的步骤，未变化的步骤可以不传（无需包含在 progress 数组中）`
- 后半句：`本次更新之前所有状态为"正在运行"（in_progress）的步骤，都必须在本 progress 报告中体现它们的最新状态`

模型（尤其指令遵循较弱的 fast 模型）按前半句行事——**只上报"当前正在执行的步骤"**；而后端 `agent/progress.go:104-122` 按后半句校验——**计划里所有 in_progress 步骤都必须出现**，缺一个即整次调用失败。
`i18n/zh_system.go:1402`（task-progress 章节）再次强调"只报告状态有变化的步骤以及当前正在执行的步骤"，进一步强化了错误理解。

**日志证据**（`log/tool-call-error-2026-10-01.log`）：

```
tool=read_file
raw_call: { "meta": { ... "progress": [{"description":"前端表达式解析器 web/static/ui-expr.js","index":3,"status":"in_progress"}], ... }, "start_line": 690 }
error: read_file: Error: progress report must include the latest status of every in-progress step; missing step(s) at index [1]
```

```
tool=... (replace_in_file style.css)
raw_call: { "meta": { ... "progress": [{"description":"实施需求 A：平移改为视窗（相机）变换","index":3,"status":"[=]"}] ... } }
error: ... missing step(s) at index [1]
```

即：progress 里**只有一条、且正是"当前步骤"**——完全符合提示词前半句，却被后端拒绝。这是"提示词-校验不一致"的直接证据，而非模型"乱写"。

### R2（次因 · 对应 A2"progress 为空"）无计划/无在办事项时仍强制非空

`agent/risk.go:109-115`（FEATURE-450）要求 `meta.progress` 必须至少 1 条记录，**且不区分是否存在任务计划**。
会话刚开始、尚未调用 `track_task_progress` 时，模型"无事可报"，自然给出 `"progress": []`：

```
[2026-10-01 13:40:49.188] tool=search_files
raw_call: {"meta": {"intent": "...","risk":"low","risk_reason":"只读搜索源码，不修改任何文件","affected_objects":["/Users/direct3d/github/co-shell"],"progress": []}, ...}
error: search_files: Error: meta.progress is required and must contain at least 1 current-status record
```

紧接 0.016 秒后**第二个并发工具调用以同样形态再次失败**（同一批并行调用、同一错误）——一次坏习惯被放大成 N 条错误记录。
2026-10-01 全日志中 `"progress": []` 出现 10 次、完全缺 `progress` 字段 4 次。

### R3（放大器 · 影响所有 A 类）错误提示模板答非所问

`agent/tool_error.go:42` 用 `strings.Contains(errMsg, "missing"/"required"/"omit")` 粗分类：

- **所有** meta 类错误（`meta.risk is required`、`meta.progress is required...`、以及 `missing step(s) at index [1]`）都落入"missing required parameters"分支；
- 该分支调用 `getRequiredParamsDescription(toolName)`（`tool_error.go:95-116`）回填的是**工具自身参数**，例如 read_file → `'path' ... 'start_line' 和 'end_line' 可选`，search_files → `'path' 与 'regex'`，execute_command → `'command'/'timeout_seconds'/'on_timeout'`；
- **模板全文不出现 `meta` 一词**。

结果：模型收到的"纠错指南"是"你漏了工具参数"，而真实原因是"progress 少了仍在进行中的步骤"。
日志显示同一调用形态被反复重试（如 read_file / search_files 连续两次同样报错），说明该提示不仅无助于纠正，还引导模型去改错误的方向。
另外，`formatToolError` 把"业务语义校验失败"统一包装成"参数缺失（missing required parameters）"，污染了错误可读性与统计口径（本次排查就被它误导过一次）。

### R4（背景 · 解释"为什么是会话最开始"）meta 是"带会话状态的强制字段"，且入场时无样例可模仿

- meta 是**每个工具**都要写的强制对象（`browser_tools_p3_defs.go` 等工具定义里 `"required": ["meta"]`），其中 `progress` 还携带**跨轮会话状态**（必须与 `track_task_progress` 建立的计划索引一致）。这本身对弱指令遵循模型就是高负担。
- `track_task_progress` / `attempt_completion` 被 `toolRequiresMeta`（`agent/toolcall_mode.go:1859-1861`，FIX-510）豁免 meta 校验，因此会话后段使用这两个工具时不会再触发。
- 会话最开始的历史消息中**还没有任何"成功的 meta 调用"样例**可模仿；随着会话推进，历史里出现大量正确样例，模型"照抄"成功率显著提高。这构成"越靠前越易错"的第二重解释。

### R5（次要）非 meta 类

- **SEARCH 块不匹配**（笔记 3、4）：模型凭记忆书写 SEARCH 内容未先读取原文所致；笔记 4 中 `Closest match found near line 85` 是已实现的辅助线索，可推广。
- **模型端点 502**（笔记 7）：基础设施问题，与应用逻辑无关。

## 5. 为什么"会话最开始"报错更密集

| 机制 | 会话初期 | 会话中后期 |
|------|----------|------------|
| R1 多步 in_progress 冲突 | 计划刚建立/步骤推进时，常有 2 个以上步骤处于 in_progress，或模型从 step N 推进到 N+1 却未把 N 标完成 → 必然触发 | 通常只剩 1 个 in_progress，且恰为"当前步骤"，自然被上报 → 不触发 |
| R2 progress 必须非空 | 尚无计划，"无内容可报"却必须报 → 报 `[]` 直接失败 | 已有计划，随时有内容可填 |
| R4 无样例可模仿 | 历史中没有任何成功 meta 样例 | 历史里已积累多个成功样例可照抄 |
| meta 豁免工具 | 开场以读/搜/执行类工具为主（全部要求 meta） | 收尾常调用 track_task_progress / attempt_completion（豁免） |

## 6. 改进建议（**未实施**；按用户决定：保持硬失败，把错误提示写清楚）

### 6.1 P0-A 消除提示词自相矛盾（`i18n/zh_system.go` + `i18n/en_system.go`）

把两处（meta 说明段、task-progress 章节 `zh_system.go:1402`）统一为**同一条无歧义规则**，建议措辞：

> progress 必须包含：① 本次状态发生变化的步骤；② 当前正在执行的步骤；③ 所有此前处于 in_progress 且本次仍保持 in_progress 的步骤（这些步骤即便状态未变化也必须出现，否则报告会被拒绝）。
> 任务计划中不存在 in_progress 步骤时，只需给出当前步骤；尚无任务计划时 progress 可省略或为空数组。

要点：删除"未变化的步骤可以不传"这一独立表述（它是当前错误的直接诱因），把它并入"③"的例外说明中。

### 6.2 P0-B 允许"无计划 / 无在办步骤"时的空 progress（`agent/risk.go:109-115`）

将"至少 1 条记录"的硬性要求放宽为条件式：

- 无任务计划 → 允许 `progress` 缺失或为空数组；
- 有计划但无 in_progress 步骤 → 允许只报 1 条当前步骤（现状即可）；
- 有计划且存在 in_progress 步骤 → 仍要求覆盖（由 `progress.go` 的校验负责）。

这样 R2 类错误（约占记录错误 1/5）可被彻底消除，且不削弱 FEATURE-452 的"不许忘记在办步骤"语义。

### 6.3 P1-A 错误提示"答非所问"的修正（`agent/tool_error.go`，**用户已选定方向：保持硬失败 + 提示写清楚**）

1. **新增 meta/progress 专属分支**（在 contains 粗判之前匹配 `meta.`、`progress report must include` 前缀），错误文本改为可直接照做的形式，并**列出被遗漏步骤的索引与标题/描述**，例如：

```
Tool call "read_file" was REJECTED: the progress report did not cover every step
that is still in progress.

MISSING IN-PROGRESS STEPS (must be included in meta.progress with their latest status):
  [1] "检索 co-shell 工具调用参数校验与错误处理代码"  (current status: in_progress)
  [3] "前端表达式解析器 web/static/ui-expr.js"        (current status: in_progress)

FIX: re-send the same call and make meta.progress cover the step(s) above,
using the same index/status values as the task plan.
```

   实现要点：`applyProgressReport`（`agent/progress.go:104-122`）抛出错误时不再只带索引，而是把遗漏步骤的标题与状态一并带出（可用结构化 error 类型或在 `run_stream.go` 捕获后拼接），再由 `formatToolError` 渲染。
   **语义不变**：仍然拒绝这次调用（硬失败），仅让纠正信息可执行。

2. **meta 类错误不再回填工具自身参数清单**：把 `getRequiredParamsDescription` 的调用限定为"工具顶层参数缺失"场景；meta 类错误改为列出 meta 的 5 个字段（intent/risk/risk_reason/affected_objects/progress）及其最小形态。
3. **分类前缀**：把"参数缺失"与"业务校验失败"在标题上区分（如 `were REJECTED by validation`），避免误导排查。

### 6.4 P1-B 在工具 schema 的 meta 描述里写明 progress 最小形态（`agent/*_defs.go`）

模型在**调用点附近**（工具 schema）能看到规则，可缓解超长系统提示词中段"指令衰减"。建议在 meta 属性描述中补一句：
`progress: REQUIRED when a task plan has in-progress steps — include those steps plus the current one (index/description/status).`
（成本极低，收益稳定，建议与 P0-A 同批实施。）

### 6.5 P2 其他（可选，本次不建议动）

- SEARCH 块不匹配的错误文本已在部分工具里带 `closest match`（笔记 4），可把该能力推广到所有 `replace_in_file` 的 SEARCH 失败分支。
- 并行批调用失败放大问题：可考虑同一批 tool_calls 中首个失败后，对同批次相同错误去重提示（降低噪声，不改语义）。
- ~~软纠正（自动保留 in_progress 状态并继续执行）~~ —— **用户已明确不采用**，此处仅记录为已评估项。
