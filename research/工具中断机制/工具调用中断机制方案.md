# 工具调用中断机制 设计方案（ESC / 暂停键 / Ctrl+C 立即中断并杀死工具子进程）

> 状态：**方案待评审**（尚未编码）
> 依据：2026-10-02 用户反馈「工具调用执行期间，Web UI 按 ESC、点击暂停按钮、TUI 按 Ctrl+C 均无效，直到工具自己退出才响应」
> 关联：FIX-581（`attempt_completion` demo 命令超时，同一根因家族：`exec.Command` 自管进程组、缺少统一取消路径）
> 建议编号：**FEATURE-582**（新能力）　建议版本：**v0.90.0**（minor 递增，待用户确认）

---

## 1. 现象与原因链（四层，均有代码位置证据）

### 第一层：Web 出口只发了「软信号」
- `web/static/app.js:4753`（暂停按钮）与 `:4890`（ESC）都发送 `{type:"interrupt"}`。
- `web/session.go:249-253` 收到后只调用 `ag.Interrupt()` + `ag.ReleaseUIWait()`。
- `agent/agent.go:1945-1952` 的 `Interrupt()` **只往 `interruptCh` 写一个令牌**；该通道仅被 `streamLLMResponse`（`agent/stream_response.go:263`）select 读取。
- ⟹ **工具执行期间没有任何协程在读 `interruptCh`**：信号躺在容量 1 的通道里无人处理；既不取消工具 ctx，也不杀子进程。

### 第二层：TUI 出口在关键窗口「主动让权」
- `repl/repl_esc.go:26-45` 的 ESC/Ctrl+C 消费者有两处直接 `return`：
  - `io.IsReading()`：REPL 正在等输入（独占消费者优先）；
  - `ag.IsCommandRunning()`：**系统命令正在运行**。
- 命令类工具执行时：`agent/command_tools.go:202`、`:392` 置 `SetCommandRunning(true)`，**并且** `repl/session.go:185-196` 的 `BeforeCommand` hook 会 `reader.Pause()`（暂停事件源）。
- ⟹ 命令执行期间按键**根本到不了** agent（事件源被暂停 + 消费者 yield 的双重死区）。
- `repl/repl.go:299-314` 另有 SIGINT/SIGTERM handler：直接打印告别语并 `os.Exit(0)`（仅在终端处于 cooked 模式、即命令执行期间才会收到）——即"中断"要么被吞掉，要么直接退出程序，没有第三种可能。

### 第三层：Agent 有取消链路，但中断入口未接上
- `agent/agent.go:1970-1982` `Cancel()`：写 `cancelCh` **并** `cancelFunc()` 取消 `cancelCtx`，注释明确 "so blocked tool executions can detect the cancellation"。
- `agent/run_stream.go:1542-1545` 工具执行使用 `toolCtx := a.CancelContext()`（FEATURE-280）作为父 ctx。
- ⟹ 链路是通的，但：① Web 的 interrupt 不走 `Cancel()`；② TUI 的 Ctrl+C 在工具期间被 yield；③ `Cancel()` 只对**响应 ctx 的工具**生效。

### 第四层：命令类工具不响应 ctx（最关键）
- `agent/command_tools.go` 的 `executeSystemCommand` / `ExecuteCommandDirectly`：使用 `exec.Command` + `setProcessGroupAttr` 自管进程组，**只 select 超时（time.After），不 select `ctx.Done()`**。
- ⟹ 即使 `cancelCtx` 被取消，shell 及其整个进程组继续运行、工具不返回 —— 用户看到的就是"中断无效，直到工具退出"。

### 其它工具现状（抽样）
| 工具/模块 | 是否响应 ctx | 证据 |
|---|---|---|
| `execute_command` / 直接命令 / demo 命令 | ❌ | `agent/command_tools.go`（仅超时） |
| `browser` 页面加载/选择器等待 | ✅ | `browser/cdp_wait.go:70,92,131,168`、`browser/cdp_events.go:109` |
| MCP（SSE/stdio 调用） | ✅ | `mcp/sse_client.go:75,183`、`mcp/stdio_client.go:114` |
| shell 持久会话等待输出 | ✅ | `shell/session.go:286` |
| `render_ui(waiting=true)` | ✅ | `agent/ui_wait.go:98` |
| `subagent` / `visual_analysis` / `docx` / `xlsx` / `scheduler` | ❓ 未审计 | 需 P1 逐个体检 |

### 收尾约束：消息序列必须闭合
LLM 的 `tool_calls` 必须逐条有对应的 `tool` 结果，否则 API 报 400（本项目已有实例：`log/llm-call-error-2026-10-02.log` 14:13:58）。因此"中断"必须明确决定：**丢弃该轮 assistant 消息**，还是**回填一条"用户中断"结果**。

## 2. 方案架构（五件套）

### 2.1 统一中断入口（单点收敛）
新增 `Agent.InterruptTool(reason string)`（内部复用并扩展现有 `Cancel()`）：

1. 置中断标记：`interrupted atomic.Bool` + `interruptReason`（供 RunStream 判定，避免与"工具自身失败"混淆）；
2. `cancelFunc()` 取消 `cancelCtx` → 唤醒所有 `select ctx.Done()` 的工具（browser/MCP/shell/子 Agent…）；
3. 调用进程注册表 `KillActive(reason)` → **整组 SIGTERM → 200ms → SIGKILL**（见 2.2）；
4. 写 `cancelCh` → 命中既有 `CanceledError` 路径（`agent/stream_response.go:258-261`、`agent/run_stream.go:371-374`）。

三个出口统一接入：
- **Web**：`web/session.go` 的 `case "interrupt":` 改为 `ag.InterruptTool("esc")` + 保留 `ReleaseUIWait()`；
- **TUI**：`repl/repl_esc.go` 去掉两处 yield（命令运行期间也投递事件），ESC/Ctrl+C 统一映射到中断入口；
- **SIGINT**：`repl/repl.go:299-314` 改为「有工具在跑 → 中断工具；空闲 → 保持退出程序」（待确认 Q2）。

### 2.2 活动子进程注册表（"立即杀死"的抓手）
新增 `agent/proc_registry.go`：

```go
type ProcEntry struct { Tool, Command string; PGID, PID int; StartedAt time.Time; Session string }
type ProcRegistry struct { mu sync.Mutex; groups map[int]*ProcEntry }
func (r *ProcRegistry) Register(tool, command string, cmd *exec.Cmd) (unregister func())
func (r *ProcRegistry) KillActive(reason string) (killed []ProcEntry)  // 默认只杀"当前工具"的活动组
func (r *ProcRegistry) KillAll(reason string) (killed []ProcEntry)     // 会话结束/退出时可用
func (r *ProcRegistry) Snapshot() []ProcEntry                          // 日志/UI 展示
```

- 复用既有 `setProcessGroupAttr` / `killProcessGroup`（`agent/command_tools_unix.go:61-69`、`command_tools_windows.go:188-195`）；
- 接入点：`executeSystemCommand`、`ExecuteCommandDirectly`、`runDemoCommand`（FIX-581）、`shell` 会话进程、`subagent` 子进程；browser 的 Chrome 默认**不**连带杀（可由配置决定）；
- `detach` 模式（`on_timeout=detach`）注册但标记 `Detached=true`：中断默认不杀，退化为"会话结束清理"。

### 2.3 ctx 传播补齐（让工具"愿意"退出）
- `executeSystemCommand` / `ExecuteCommandDirectly`：新增与超时并列的 `select { case <-ctx.Done(): killProcessGroup(cmd); interrupted = true }`；返回专用错误 `ErrToolInterrupted`（与超时、普通失败区分，用于文案）。
- `detach` 分支：ctx 取消**不杀**（尊重用户显式选择），仅登记注册表。
- P1 审计清单：`subagent`、`visual_analysis`、`docx`、`xlsx`、`scheduler`、MCP 工具层、browser 其余等待点，逐一补 `ctx.Done()` 分支并加测试。

### 2.4 中断后本轮处置（保证消息闭合）
- 在 `agent/run_stream.go` 工具执行处：工具返回后检查 `interrupted` 标记；
  - **方案 A（默认推荐）**：丢弃当前迭代的 assistant 消息（含 `tool_calls`）与已完成的部分 tool 结果，直接回到输入态（`return "", nil`），输出系统提示"⛔ 已中断"。最快、最"干净"；
  - **方案 B**：把"用户已中断该工具调用（SIGKILL，含部分输出）"作为 `tool` 结果回填，让 LLM 知晓并自行收尾（多一轮，但上下文更完整）；
  - **方案 C**：默认 A，另加系统参数 `interrupt-result-mode` 切换 A/B。
- 无论 A/B，都必须满足：`messages` 中 assistant 的 `tool_calls` 与 `tool` 结果数量严格配对（含"本轮已执行完成的其它工具"）。

### 2.5 交互与反馈
- **Web**：工具执行期间 ESC / 暂停按钮 = 立即中断（**不弹确认框**）；LLM 输出阶段保持既有"暂停并确认"语义（不破坏 FEATURE-201/427）。中断后前端由现有 `await_input` 事件把按钮从 ⏸ 复位为 ➤。
- **TUI**：命令执行期间也投递 ESC/Ctrl+C 事件（不 Pause reader 的按键通道），中断后打印一行结果（如 `⛔ 已中断 execute_command（PID 1234 进程组已终止）`）。
- **幂等与竞态**：中断重复触发只生效一次；工具正常结束时 `unregister`；轮次开始（`ResetCancel`/`ResetInterrupt`）时复位中断标记。

## 5. 验收方式（用例草案）

1. **UC-01 Web ESC 中断命令类工具**：`--serve` 启动 → 触发 `execute_command("sleep 600")` → 按 ESC → **≤1s** 内恢复到输入态；`pgrep -f "sleep 600"` 无残留；无 400 错误（消息闭合）。
2. **UC-02 Web 暂停按钮**：同上，验证与 ESC 等效。
3. **UC-03 TUI Ctrl+C 中断命令类工具**：命令执行期间 Ctrl+C → 工具被中断、**程序不退出**（按 Q2 结论）；空闲时 Ctrl+C 行为符合所选语义。
4. **UC-04 管道/孙进程**：`sleep 600 | cat` 中断后两个进程均消失（整组 kill）。
5. **UC-05 只杀当前工具**：先后启动 A、B 两个工具进程（B 为 detach 后台服务）→ 只中断 A → B 仍存活（按 Q4 结论）。
6. **UC-06 幂等**：连按 3 次 ESC → 只产生一次中断提示、无重复 kill、无 panic。
7. **UC-07 中断后消息序列闭合**：中断后继续下一轮对话 → 无 `insufficient tool messages following tool_calls` 报错（对照 `log/llm-call-error-2026-10-02.log`）。
8. **UC-08 非命令类工具**：`browser_navigate` 等待页面加载时中断 → ≤1s 返回输入态（验证 ctx 链路）。
9. **UC-09 工具确认框期间中断**：确认框弹出时 ESC → 取消工具且不执行。
10. **UC-10 回归**：`go build ./... && go vet ./...`、`go test ./agent/ ./repl/ ./web/ ./shell/ -short` 与 `main` 基线失败集逐项一致（零新增）。

## 6. 风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| 误杀本应保留的后台任务 | 整组 kill 会连带 `&` 起子进程 | 默认只杀"当前工具"；`detach` 登记但不杀；会话结束统一清理作为兜底 |
| 命令执行期间的按键通道 | 现 `BeforeCommand` 会 `reader.Pause()`，中断事件源被暂停 | 改为"暂停普通字符投递、保留 ESC/Ctrl+C 投递"，并用 UC-03 验证 |
| 消息序列破坏 | 中断导致 tool_calls 无结果 → API 400 | §2.4 明确回滚/回填规则 + UC-07 专项验证 |
| SIGINT 语义变化 | TUI Ctrl+C 从"退出程序"变为"中断工具"可能让用户无法退出 | 按 Q2 选择语义（推荐"工具期间中断、空闲退出"） |
| 回归面大 | 触及 agent/web/repl 三处核心路径 | 全部改动配单测；P0 合并前跑基线对比；用例覆盖两个出口 |

回滚：改动集中在 P0 的四类文件（agent 中断入口/注册表、command_tools ctx 分支、web/session.go、repl_esc.go），可按文件粒度回退且无数据结构迁移。

### 7.1 确认结果（2026-10-02）

| 编号 | 问题 | **结论** |
|---|---|---|
| Q1 | 中断后本轮处置 | **A**：立即终止本轮回到输入态，**丢弃尚未闭合的 tool_calls 消息**（保证消息序列完整） |
| Q2 | TUI Ctrl+C 语义 | **A**：工具执行期间 = 中断工具（不退出）；空闲等待输入时 = 退出程序（保持现状） |
| Q3 | ESC/暂停/Ctrl+C 统一性 | **A**：工具执行期间三者**统一为“立即中断 + 杀子进程”且不弹确认框**；LLM 输出阶段的 ESC 仍保留“暂停 + 确认” |
| Q4 | 清理范围 | **B**：杀死**所有由工具启动且仍在运行的进程组**（含 `detach` 后台服务/监听），**并包含 sub-agent**（用户备注） |
| Q5 | 实施范围 | **A**：**一次性覆盖全部工具**（逐个体检并补齐 ctx 响应 + 审计不可中断的长阻塞点）；用户备注提出“是否把所有工具调用改为线程执行、中断时直接杀线程”——见 §8 |
| Q6 | shell 持久会话中断方式 | **B**：**直接整组 kill**（该 shell 会话随之终止，需标记会话已终止并可重新 `shell_start`） |

### 7.2 由结论带来的方案调整（相对 §2 初稿）

1. **注册表默认动作改为 `KillAll`**（原设计默认 `KillActive`）：中断时遍历全部活动条目（含 `Detached`、含 sub-agent 子进程）逐个整组 SIGTERM → 短暂等待 → SIGKILL；日志与 UI 提示汇总条目数与 PID 列表。
2. **shell 会话中断改为整组 kill**（不再走 `\x03` 软中断）：`shell/session.go` 需支持“被外部终止”后的状态复位与后续 `shell_start` 重建；`shell_send` 在会话已终止时返回明确提示。
3. **不再分期**：P0 即为“全工具覆盖”，实施内部按批次推进（§10），对外一次交付。
4. **执行模型改为“独立 goroutine 执行 + 中断即返回”**（§8），以同时满足“立即响应”与“一次性覆盖全部工具”。

## 8. 执行模型：为什么不能「直接杀线程」，以及等价实现（回答 Q5 备注）

**结论：Go 无法"杀线程"，因此不能靠杀线程来中断工具；但可以达到你想要的用户体验。**

1. **技术上不成立**：Go 运行时**不提供**安全终止 goroutine 的手段（没有 `kill goroutine`）。goroutine 只能**协作式退出**——靠 `ctx` 取消、channel 关闭、或它等待的资源被打断。强行终止会让互斥锁、文件句柄、子进程处于不一致状态。即便在支持 pthread_cancel 的语言里，杀线程也会留下同样的烂摊子。
2. **工具耗时的来源决定"可打断性"**：绝大多数长工具卡在**子进程**或**网络 I/O**上——这两类都能真正打断（kill 进程组 / ctx 传到底层）。真正的纯 Go CPU 死循环工具极少（本项目暂未发现）。
3. **落地做法（= 你想要的效果）**：**工具在独立 goroutine 中执行 + 中断即返回，不 join**。
   ```
   resCh := make(chan toolResult, 1)
   go func() { resCh <- a.runTool(toolCtx, tc, args) }()   // 工具在独立 goroutine
   select {
   case res := <-resCh:            // 正常完成
   case <-a.interruptSignal:       // 用户中断
       a.cancelCtx cancel + procReg.KillAll()   // 广播取消 + 整组杀子进程
       return interruptToIdle()                  // 立刻回输入态，不等 resCh
   }
   ```
   - **UI 立即恢复**（不因工具体内残留而卡住）；
   - 被取消的工具 goroutine 依靠"子进程被杀 / ctx 取消 / 网络调用返回"自然退出；
   - **在途登记与兜底**：`inFlight` 表记录尚未退出的工具；中断后 5s 仍在则输出告警日志（可选再执行一次 `KillAll`），保证残留可观测、不静默；
   - 这样"一次性覆盖全部工具"（Q5-A）才成立：**不需要**每个工具都完美支持取消，也能让用户立即脱身。
